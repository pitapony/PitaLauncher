# M2.5 — the controller remap UI (`crates/input/src/remap.rs` + `crates/app/src/controls.rs`)

Status: implemented; `pitagames-input` is verified by its own tests on macOS and
in `archlinux:latest`, and `crates/app` is build/lint/test verified in the Arch
container. The screen and the capture path have not been exercised against a
real controller on the target machines — a headless container has no evdev node
— so the pad half is covered only by the framework-free tests and the pump's
`ReplaySource` tests. Nothing here has met a TV either.

This is the slice the last three advertised as "next": the input layer
(`docs/m2.5-input.md`), the focus graph (`docs/m2.5-focus.md`), the gamepad pump
(`docs/m2.5-gamepad.md`), the shells (`docs/m2.5-shells.md`) and the hints
(`docs/m2.5-hints.md`) all shipped, but `input.toml` was hand-edited and the
hint row read the *built-in* pad layout because the app never learned the pad's
GUID. This slice closes both: it is the one writer of `input.toml`, and it hands
the worker's device GUIDs up to the app.

## Why this slice exists

M2.5's acceptance bar is controller-only operation. A controller-only launcher
cannot ask the user to edit a TOML file, so every binding has to be changeable
from the couch — and the only honest way to bind a control is to *press it*,
because the map may not know it yet (a `Button` the built-in layout leaves
unbound produces no `Action` at all). That is the whole design constraint: the
remap screen does not offer a list of 17 buttons to pick from; it asks the input
pumps for the next physical control.

Hardware-independent apart from the device itself, so it ships while the M0
hardware closer waits on machine access.

## The model (`crates/input/src/remap.rs`)

Framework-free, no Dioxus, unit-tested. `input.toml` holds only *overrides*, so
the session is deliberately the only code that decides what the file contains:

- `RemapTarget::{Keyboard, Pad { guid, name }}` — the device under edit. A pad is
  keyed by its SDL GUID (as the file is), so a remap survives a replug; the name
  is for the screen.
- `CaptureSlot::{Replace { action, index }, Add { action }}` — what the next
  captured control does. Editing is **slot-based**: a gamepad's `NavigateUp` is
  bound to *both* the d-pad and the left stick on purpose, so a rebind replaces
  one slot and "add" appends another.
- `RemapSession::new(target, &InputMaps)` — starts from the device's stored
  override or its built-in layout, and normalises the map's `device` field to the
  target so a hand-edited file cannot store it under the wrong key.
- `begin_capture` / `cancel_capture` / `capture_control(binding)` — the capture.
  `capture_control` refuses a control of the wrong kind (a pad map never holds a
  `Key`, the keyboard's never holds a `Button` — the invariant the mapper relies
  on) and leaves the capture pending with a message, so the person presses the
  right device. An accepted control is written to its slot and then *stolen* from
  every other action (`InputMap::dedup_binding`), because one control should not
  drive two actions.
- `remove_binding` / `reset_action` / `reset_all` — the rest of the edit surface.
  Resetting one action does not hand a stolen control back to the action that
  used to own it; a full reset does.
- `set_deadzone` / `set_repeat_delay_ms` / `set_repeat_interval_ms` — the feel
  numbers, clamped like the loader clamps a hand-edited file.
- `apply(&mut InputMaps)` — folds the edit in, **dropping the override entirely
  when the device matches its built-in layout**, so resetting everything empties
  the file rather than storing a copy of the defaults. `is_customized` is the
  same comparison.

`InputMap` gained the primitives the session needs — `set_bindings`,
`set_binding`, `remove_binding`, `dedup_binding` — so no edit logic lives in the
screen.

## The seam

### `crates/app/src/controls.rs` — the screen

Two levels, both driven by the shared focus graph so a pad can do everything a
pointer can:

- the **list** picks a device (the keyboard, then each connected pad) and shows
  every `Action` with its current bindings, then Reset all / Save / Discard;
- the **detail** edits one action: a rebind and a remove per binding slot, plus
  Add binding and Reset action.

A rebind calls `begin_capture` and returns; the actual control arrives from the
pumps (below). Save writes `input.toml` through `InputMaps::save_default`, sets
the maps signal (so the hint row follows), and pushes the maps into the running
worker (so the live pump follows). Discard reloads the stored map. The feel
numbers are real `<input type=number>` fields and are deliberately *not* focus
cells yet: a pad cannot type a number, so tuning waits for the on-screen
keyboard slice.

### The app (`crates/app/src/main.rs`)

- **The maps are a signal.** `input_maps: Signal<InputMaps>` replaced the plain
  value, so the hint row re-renders when a remap is saved, and the keyboard pump
  reads the current keyboard map on every key event (`key_maps.peek()`), so a
  remap of `Enter`/`Escape` applies without a restart.
- **The session lives in the app, not the screen.** `remap:
  Signal<Option<RemapSession>>` is read by both input pumps: while a capture is
  pending, a pad action or a key is *swallowed* rather than dispatched (so the
  pressed control cannot also navigate), `Back` cancels the capture, and the raw
  control is handed to `capture_control`. The session is `Clone + PartialEq`
  precisely so it can live in a signal.
- **The worker names its pads and its raw controls.** `gamepad::GamepadEvent`
  gained `Device(Device)` (the GUID the remap UI keys a map by, and now the hint
  row's map) and `Control(Binding)` (a raw button press, sent *after* the action
  for the same press so the swallow lands first). The worker reports a device
  once, by GUID, and only exposes raw controls it actually saw.
- **The worker takes a live remap.** `gamepad::spawn` returns a `MapReload` (a
  `std::sync::mpsc::Sender<InputMaps>`); the worker drains it each tick and calls
  `Pump::set_maps`, which re-resolves every device by GUID. The handle travels to
  the screen as a `Signal<MapReload>` so any number of event handlers can use it.
- **The hint row now reads the right map.** With the GUID known, the pad branch
  is `input_maps.for_device(guid, true)` — the last pad's remap — instead of the
  built-in layout (`docs/m2.5-hints.md`'s known limit is closed).
- A **Controls** tab in the nav opens the screen; `Back` leaves it.

### `crates/input/src/map.rs`

The four editing primitives, with two tests: a slot can be replaced, removed and
set-as-a-list, and a capture steals its control from the action that owned it.

## Verification

`pitagames-input` is at **74** tests (was 62): 10 `remap` + 2 `map` + the
existing suites. They cover loading a stored override or the default, a capture
applying only while pending, the wrong-kind refusal, stealing a control,
adding without dropping existing bindings, removing the last binding, resetting
an action and the whole map, `apply` storing an override and a reset removing it,
clamped tuning, and a cancelled capture changing nothing.

`crates/app` adds tests for the pump (`a_button_press_is_reported_as_a_control_beside_its_action`,
`a_remap_pushed_into_the_pump_takes_effect`, the `MapReload` equality) and the
Controls screen (`the_target_list_is_the_keyboard_then_every_gamepad`,
`the_list_cells_are_the_targets_the_actions_and_the_globals`,
`a_detail_lists_a_rebind_and_remove_per_binding_then_the_globals`,
`a_row_summarises_an_unbound_action_honestly`). `cargo test`, `cargo clippy
--all-targets -- -D warnings` and `cargo fmt --all -- --check` are clean in
`archlinux:latest` (`crates/app` at **152** tests); the pure crates pass on
macOS.

## Known limits

- **No smoke run yet.** The screen has not been walked with a pad or driven with
  a mouse in an Xvfb run; the capture path in particular (`Action` swallowed,
  then `Control` applied) is covered only by the pure tests and the pump tests.
- **`Back` cancels a capture.** That is the escape hatch for a controller-only
  user, but it means the default `Back` control (pad `East`, keyboard `Escape`)
  cannot itself be *captured into another action* by pressing it. `Back` can
  still be rebound, bindings can be removed with the on-screen Remove, and the
  Escape/East binding can be reset; the limitation is documented rather than
  worked around.
- **Keyboard captures are limited to the `Key` set.** `binding.rs`'s `Key` is
  deliberately small (arrows, WASD, Enter/Escape/Tab/Space, Q/E/F, F11), so a key
  outside that set does nothing during a keyboard capture. The set covers every
  key the shells actually bind.
- **The feel numbers are pointer-only** and the pad-guid remap does not include
  gyro/touchpads (not in scope at all).
- **A stale capture on leaving the screen is only cosmetic.** The pumps gate the
  capture on the Controls view, so it cannot swallow input elsewhere; returning
  to the screen resumes the "press a control" prompt, and `Back` cancels it.
- **Not driven against a real controller** on the RX 9070 / RX 5700 XT. The
  container has no `/dev/input`, so the `GilrsSource` button/axis conversion is
  covered only by its own `crates/input` tests.
