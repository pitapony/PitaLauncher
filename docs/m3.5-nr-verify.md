# M3.5 — NR verification, the support bundle and the in-game hints

The three things that sit *after* an NR install (ticket #29): telling the user
whether the network actually engaged, collecting the evidence upstream asks for,
and showing the in-game keys. Plan §6 items 6, 8 and 10; ADR-0024.

Ticket: #31 (part of umbrella #8).

## Pieces

| Crate | Responsibility |
|---|---|
| `platform::verify` (`crates/platform/src/verify.rs`) | read engagement from a mod's log, markers as data, one panel for the upscaler and NR |
| `platform::support` (`crates/platform/src/support.rs`) | the opt-in bundle: an explicit allowlist, by construction |
| `platform::hints` (`crates/platform/src/hints.rs`) | per-injection-mode in-game key hints, as data, with a per-game note override |
| `platform` compat (`[ingame] notes`) | the per-game note a title may use to override the shipped one |
| `cli` | `pitagames-cli support verify` / `support bundle` |
| `app` | the verification rows and the bundle button on the Graphics screen, the in-game hint card on the game page |

## Verify (\(`platform::verify`\))

After a launch the launcher answers "did it engage?" by reading the mod's own
log — `dlssnr-amd.log` for DLSSNR, `OptiScaler.log` for the injected upscaler —
without ever opening the in-game menu (plan §6 item 8).

The markers are **data** (`crates/platform/data/verify-markers.toml`), so an
upstream wording change is a one-line edit to that file rather than a code
change. The upscaler and neural-rendering subjects share one engine and one
panel, so the graphics screen reports them side by side.

```toml
[[checks]]
check = "nr"
log = "dlssnr-amd.log"

[[checks.engaged]]
id = "model-load"
contains = "model loaded"

[[checks.failed]]
id = "model-missing"
contains = "model not found"
```

```rust
pub fn verify_text(set: &MarkerSet, text: &str) -> Engagement;
pub fn verify_file(set: &MarkerSet, dir: &Path) -> Engagement;
pub fn panel(data: &MarkerData, checks: &[Check], dir: &Path) -> Vec<Row>;
pub fn checks_for(profile: &Profile) -> Vec<Check>;
```

`Engagement` is `Engaged { marker, line }`, `NotEngaged { failed }` or `NoLog`.
An engaged marker **anywhere** in the log wins over a later failure: the question
is "did the network run at least once", and it did. `verify_file` reads a bounded
tail ([`logs::tail`], 256 KiB) so a many-gigabyte log never blocks the UI, and a
missing log is `NoLog`, not an error. `checks_for` reads the profile's single
injection slot (ADR-0023): a profile reports NR or the upscaler, never both, and
a profile that injects nothing reports neither.

## The support bundle (\(`platform::support`\))

Upstream asks for a specific set of files in a bug report (plan §6 item 10). The
bundle collects **exactly** that set:

| Included | Source |
|---|---|
| `versions.txt` | GPU / Mesa / VRAM / Proton, rendered from the detected profile |
| `dlssnr-amd.log`, `OptiScaler.log`, `ReShade.log`, `helixsr.log` | the game directory |
| `dlssnr-amd.ini` | the game directory |
| the Proton log | only when the caller names it (`PROTON_LOG=1`) |

**Nothing else, by construction.** The collector never walks a directory: it
looks up the exact names in `ALLOWED_FILES` inside the game directory, plus one
optional log the caller names. So the NR model weights
(`nvngx_dlssnr.dll`, `dlssnr.bin`, `dlssnr-small.bin`) and any secret that shares
the directory can never enter the bundle — even when they sit right beside an
included log. The Steam Web API key and a store CLI auth transcript live in the
launcher's own trees, which the collector has no field to read.

A test asserts this by putting every forbidden file beside the allowed ones,
building the bundle and reading the written zip back (names **and** raw bytes).

```rust
pub fn collect(request: &BundleRequest<'_>) -> Bundle;
impl Bundle {
    pub fn names(&self) -> Vec<&str>;
    pub fn contains(&self, name: &str) -> bool;
    pub fn write_zip(&self, dest: &Path) -> Result<(), SupportError>;
}
pub fn versions(gpu: Option<&GpuProfile>, proton: Option<&ProtonInstall>) -> String;
```

## In-game hints (\(`platform::hints`\))

Each injection mode has its own upstream keys (plan §6 item 6): DLSSNR's `End` /
`Insert` / `F6` / `F5` / `Ctrl+F11`, Tier B's and HelixSR's `Insert`. They are
**data** (`crates/platform/data/ingame-hints.toml`), so a changed keybinding is a
data edit, and the game page shows them per the profile's mode.

```toml
[[modes]]
mode = "dlssnr"
note = "DLSSNR ships OptiScaler and its own NR Control menu; these are its keys."
hints = [
  { keys = "End", action = "NR Control menu" },
  { keys = "Insert", action = "OptiScaler menu (upscaler + frame gen)" },
  { keys = "F6", action = "Toggle neural rendering" },
  { keys = "F5", action = "Before / after screenshot" },
  { keys = "Ctrl+F11", action = "Cycle networks" },
]
```

`mode_of(profile)` reads the profile's injection (NR wins, then an explicit
`Injection`, then an injected upscaler); `hints_for(data, mode, note_override)`
returns the mode's keys and the note a game's compat entry may override through
`[ingame] notes`. Only the **note** is overridable — the keys are upstream's, and
a game can add a caveat but not rebind a mod.

```toml
# a game's compat entry
[ingame]
notes = "This game needs the 310.9.16 model."
```

## CLI diagnostic

```bash
pitagames-cli support verify --log-dir /games/Game            # engaged / not engaged
pitagames-cli support verify --log-dir /games/Game --json
pitagames-cli support bundle --game-dir /games/Game --out /tmp/pg.zip
pitagames-cli support bundle --game-dir /games/Game --proton-log ~/.pitagames/logs/steam-620.log
```

## Verification

Pure crates (macOS host and CI):

```bash
cargo test -p pitagames-platform -p pitagames-cli
cargo clippy -p pitagames-platform -p pitagames-cli --all-targets -- -D warnings
cargo fmt --all -- --check
```

`verify` covers: an engaged marker read from a fixture log and from a file; a log
without a success marker; a failed marker naming why; engagement anywhere winning
over a later failure; a missing log being `NoLog` and an empty one `NotEngaged`;
the shipped file covering both subjects; a duplicated subject and a set with no
engaged marker refused; the panel reporting only the requested subjects it has
data for; the single-slot `checks_for`; and the JSON round trip. `support` covers:
the versions lines; the allowlist collected and nothing else; every forbidden file
excluded from the model and the written zip; the optional Proton log only when
named; a missing game directory; a large file tailed; and the suggested name.
`hints` covers: the mode from the profile injection and from an injected
upscaler; NR winning the mode; a per-game note override keeping the mode's keys;
an unknown mode; `set_for` answering only a profile that injects; the shipped
plan keys; and a duplicated mode refused.

The GUI is built and linted in `archlinux:latest` (`CARGO_TARGET_DIR=/work/target-arch`).

## Known limitations

- **Not validated on hardware.** The marker strings are a first pass from
  upstream's log vocabulary and the keys are the plan's; a wrong one is a data
  edit, and the panel always pairs "not engaged" with the failed line it found so
  a mismatch is visible rather than silent. No file was read from a real DLSSNR,
  OptiScaler, ReShade or HelixSR install.
- **The bundle is a zip written locally.** There is no upload and no redaction
  pass beyond the allowlist; the transcript redaction item is M4
  (`docs/m1-diagnostics.md`, `docs/m2-cli-backend.md`).
- **The upscaler subject's markers are shipped but unvalidated**, beside the M3
  "Apply & verify" launch check; they exist so the panel and the CLI report both
  subjects through one engine.
- Not tested on a TV (ADR-0004).
