# i18n: the catalog seam

PitaGames v1 ships **one language**. What it ships is the *seam*: every
user-facing string in the GUI is looked up by a key in a catalog rather than
written as a literal inside a component, so adding a language later is a data
change (one more catalog file) instead of a rewrite of every screen.

## Where it lives

- **`crates/core/src/i18n.rs`** — framework-free, so it is testable on macOS
  and `crates/app` stays the only crate that touches Dioxus/RSX.
- **`crates/core/data/i18n/en.toml`** — the `en` catalog, embedded with
  `include_str!` so the shipped binary carries its own strings.

## The seam

```rust
use pitagames_core::i18n::t;

let label = t("action.play");          // "Play"
let line = t("library.meta_appid").replace("{id}", app_id);
```

- `t(key)` is the one lookup a screen calls. A key is `&'static str`, so only a
  literal (or a `const`) can be passed and the key set is fixed at compile time.
- A missing key **falls back to the key itself**, so the UI never panics; the
  source-scan test below is what keeps that fallback from becoming a habit.
- A value may carry a `{placeholder}` the caller substitutes with
  `str::replace`, because `format!` needs a literal format string.

## The catalog is data

`en.toml` is one flat TOML table of `"key" = "string"`. Keys are dotted by area
(`library.title`, `action.play`, `detail.command`) and quoted so TOML reads them
literally rather than as nested tables.

Adding a language is a data change:

1. add a variant to `Language` and list it in `Language::ALL`,
2. point `Language::source` at a new TOML file whose key set matches `en`,
3. fill in the strings.

Nothing else in the app changes. The
`every_language_catalog_has_the_same_keys_as_en` test refuses a half-translated
catalog: every shipped language must name exactly the `en` key set.

## The guard test

`crates/app` cannot be built on a non-Linux host, so the "every key the UI uses
exists / no unused key" check is a **source scan** (like the guards in
`crates/core/src/design.rs`), not an app build:

- `every_key_the_ui_uses_is_in_the_catalog` reads every `crates/app/src/*.rs`
  file, finds `t("…")` calls in production code (test code is split off at
  `#[cfg(test)]`), and fails listing any key the `en` catalog does not define.
- `every_catalog_entry_is_used_by_the_ui` fails listing any catalog entry no
  screen calls.

Together they are the bidirectional guarantee: the catalog and the UI cannot
drift in either direction. A `scan_t_calls` unit test pins the small hand
parser (it must find `t("nav.home")` and `i18n::t("action.play")` and must not
match `format(` or a `t("…")` inside a string literal).

## Scope in v1

- **No translations.** One catalog, `en`.
- **No heavy dependency.** No ICU, no fluent, no gettext; the catalog is `toml`
  (already a dependency) plus a `BTreeMap`.
- Only `crates/app`'s user-facing strings are catalogued. Program names
  (`gamemoderun`, `gogdl`), commands shown for copying
  (`pitagames-cli epic auth`), and log lines (`[pitagames] …`) are not copy and
  stay literals.
