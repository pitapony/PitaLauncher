# Accessibility: the bounded pass

The M4 accessibility slice is deliberately **bounded** (spec §M4): it is not a
WCAG audit. Two of the three things a couch or keyboard user needs already hold
by construction from earlier slices; the third is a label on a control whose
visible text is a glyph. This doc records what the pass covers, what proves it,
and what is explicitly out of scope.

## What already held

- **Keyboard/controller reachability is the focus graph's job, and it is
  proven.** Every screen's interactive cells are registered in one
  `pitagames_input::focus::FocusGraph` and the pad/keyboard pumps drive the same
  `Action` set into it (ADR-0022/0027, `docs/m2.5-focus.md`,
  `docs/m2.5-gamepad.md`). `focus::assert_trap_free` walks every cell to every
  other through the public moves, so a new screen cannot strand the ring, and
  the desktop nav, filter chips, home shelves and ragged chip-over-tiles layouts
  are covered by that property test. The shell's own chrome is the exception,
  and only in the desktop shell: the frameless window's **Minimize** and
  **Close** are native `<button>`s, so they are in the keyboard tab order and
  do not need a graph cell. The console shell has no window chrome.
- **Reduced motion holds by construction.** Safe mode promises "animations and
  blur off", and the `no_screen_ships_motion` source guard in
  `crates/app/src/shell.rs` fails if any screen value is a live `animation`,
  `transition`, `backdrop-filter` or `scroll-behavior` (ADR-0007, ADR-0028).
- **The AA contrast gate holds.** `crates/core/src/design.rs`'s
  `every_shipped_text_pair_meets_aa` asserts every shipped text/background pair
  is at least 4.5:1 (WCAG 2.1), with the contrast math pinned against
  independent worked examples. The old muted grey failed and was replaced
  (ADR-0028).

## What this pass added

- **`aria-label`s on the icon-only controls.** The only controls whose visible
  text is a glyph are the desktop window chrome's **Minimize** (`–`) and
  **Close** (`✕`); a screen reader had nothing to announce. Both now carry an
  `aria-label` (`action.minimize`, `action.close`), kept beside their `title`
  tooltip in `crates/app/src/main.rs`.
- **A bounded source-check guard**, in the spirit of the ADR-0028 motion/hover
  guards and the i18n source scan: `crates/core/src/a11y.rs`'s
  `unlabelled_icon_controls` reads each `button { … }` RSX block in
  `crates/app/src` and reports one whose only visible content is a single
  glyph literal (no interpolation, no alphanumerics) and which carries no
  `aria-label`. `every_icon_only_control_carries_a_label` fails on any such
  button. The tiny parser is hand-rolled (like `i18n::scan_t_calls`) and pinned
  by unit tests: it ignores word buttons, interpolated labels, attribute
  literals (`title: "Close"`) and test code, and it tracks string literals so a
  brace inside a `style` string cannot unbalance the block.

The guard lives in `pitagames-core`, not `crates/app`, so it runs in the
pure-crate test suite on any host — the same reason the i18n guards do.

## Out of scope (explicitly)

- No full WCAG audit, no ARIA landmark/role sweep, no screen-reader testing on
  hardware.
- No shipped translations (that is the i18n slice, `docs/m4-i18n.md`).
- The `title` tooltips remain as they are; only the icon-only controls gained a
  programmatic name.

## How it is verified

- `cargo test -p pitagames-core` runs the guard and the contrast gate on macOS.
- The `archlinux:latest` container build runs `crates/app`'s own source guards
  (`no_screen_ships_motion`, `no_screen_ships_a_hover_only_affordance`) and the
  app test suite, and the Xvfb smoke runs remain the visual gate.
