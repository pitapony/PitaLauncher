# M2.5 — the pad-permission probe (`crates/input/src/permission.rs` + the Controls screen)

Status: implemented; `pitagames-input` is verified by its own tests on macOS and
in `archlinux:latest`, and `crates/app` is build/lint/test verified in the Arch
container. **Not driven against a real controller whose node is denied** — a
container has no `/dev/input` and macOS has none either, and a container that
does run as root cannot reproduce `EACCES`. The denial classification is covered
by the injected layout, not by a real permission failure.

This is one of M2.5's last leftovers, alongside replay fixtures + focus-graph
property tests and the console library/game page. The plan's Permissions row:

> Joystick access normally comes from logind `uaccess`; on failure show a one-line
> fix (add the user to `input`) instead of silently ignoring the pad. We never
> grab the device, so games still receive input.

## Why this slice exists

`gilrs` speaks evdev. On a normal Arch/CachyOS session `uaccess` tags
`/dev/input/event*` for the active user, so the pad just works. When it does not
— the user is not in the `input` group, or the ACL was never applied — the node
is unreadable, `gilrs` sees no device, and the launcher looks broken with no
explanation. The pump already reports a backend that *cannot start* as
`GamepadEvent::Unavailable`, but a per-node denial is not a backend failure: the
backend starts fine and simply finds nothing. So the diagnosis is its own
read-only probe, not a message pushed from `gilrs`.

Hardware-independent apart from the node itself, so it ships while the M0
hardware closer waits on machine access.

## The model (`crates/input/src/permission.rs`)

Framework-free, no Dioxus, unit-tested. `assess(&dyn InputLayout)` folds three
facts into one verdict:

```text
event* nodes present? ──no──► PadAccess::NoDevices
        │yes
        ▼
any node readable? ──yes──► PadAccess::Usable
        │no
        ▼
PadAccess::Denied { devices, group }
```

- `PadAccess::{Usable, Denied, NoDevices}` is the verdict; `message()` is the
  one-line fix for `Denied` and `None` for the other two. The ordering is the
  no-false-positive rule: **a single readable node short-circuits to `Usable`**,
  so a working pad beside an unreadable one is never reported as denied.
- `GroupState::{Member, NotMember, Unknown}` chooses the wording: not a member →
  add yourself to the `input` group; a member → replug / log back in so the
  `uaccess` grant applies; unknown → a line naming both causes.
- `InputLayout` is the injectable seam: `event_devices`, `readable(device)` and
  `input_group()`. Tests supply a `FakeLayout`; the real one is `DevInput`.

`DevInput` is the real `/dev/input` layout:

- `event_devices` reads the directory and keeps `event*` names, sorted.
- `readable` is a **read-only `open`** — the whole test. There is no `EVIOCGRAB`
  and no ioctl anywhere in the module, so a game keeps reading the same node
  while the launcher probes.
- `input_group` reads `/proc/self/status`'s `Groups:` line and the `input` gid
  from `/etc/group`. Both are Linux-only; elsewhere (`/proc` absent, macOS) the
  answer is `Unknown`, and a machine with no `/dev/input` is `NoDevices`.

## The seam

### `crates/app/src/session.rs` — the handle (ADR-0027)

The verdict is a `Signal<PadAccess>` concern handle in `Session`
(`pad_access`), the same shape as `input_maps`/`map_reload`. The Controls screen
reads it through the one `use_session()` seam; no new prop field.

### `crates/app/src/main.rs` — the probe

`let pad_access = use_signal(|| pitagames_input::assess(&pitagames_input::DevInput::new()));`
runs the probe once at startup (it is a `read_dir` plus a few read-only opens)
and hands the signal to `provide_session`.

### `crates/app/src/controls.rs` — the screen

`permission_notice(&PadAccess, has_pad)` is the pure mapping the screen renders:
it returns `None` when the worker has already named a gamepad (`has_pad`), and
otherwise `access.message()`. The component renders the returned line in a
warning strip under the header. The `has_pad` guard is belt-and-braces over the
probe's own `Usable` short-circuit: if a pad is reaching the launcher, the
Controls screen stays quiet.

## Verification

`pitagames-input` is at **107** tests (was 98): 9 `permission` tests, plus the
existing suites. They cover a readable node being usable with no message, a
readable node beside an unreadable one never being denied, no node being
`NoDevices` (not a permission problem), devices-but-unreadable outside the group
asking for the `input` group, the same inside the group pointing at `uaccess`, an
unknown group state still yielding one actionable line, the real layout finding
`event*` nodes in a tempdir, the real layout with no nodes being `NoDevices`, and
a probe leaving a node openable by a second reader (the no-grab invariant).

`crates/app` adds 3 Controls tests: a denial shows the one-line fix, a usable pad
or an empty controller list shows nothing, and a denial is silenced once the
worker names a pad. `cargo test`, `cargo clippy --all-targets -- -D warnings` and
`cargo fmt --all -- --check` are clean in `archlinux:latest`.

## Known limits

- **No real denial smoke run.** The container has no `/dev/input` and macOS has
  none; a root container bypasses file modes, so the `EACCES` path is exercised
  only through the injected `FakeLayout`. The real `DevInput::in_input_group`
  (`/proc/self/status` + `/etc/group`) is likewise not exercised against a real
  group setup.
- **The probe runs once.** A user added to `input` must log out and back in (the
  message says so), which also restarts the launcher; a replug that repairs an
  ACL is picked up because the probe already ran at startup against the same
  nodes. There is no live re-probe.
- **`GroupState` can be wrong under unusual NSS.** `/etc/group` is read directly,
  not through NSS, so an LDAP-only `input` membership reads as `Unknown` and the
  message names both causes rather than the right one.
