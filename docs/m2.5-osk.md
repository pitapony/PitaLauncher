# M2.5 — the in-app on-screen keyboard (`crates/input/src/osk.rs` + `crates/app/src/osk.rs`)

Status: implemented; `crates/app` builds, lints and tests in `archlinux:latest`
(**169** tests) and Xvfb smoke runs in the same container typed a search filter
and created a profile through the sheet in the desktop shell and drew it in the
console shell. Nothing here has met a real controller or a TV.

This is the ninth M2.5 slice, on top of the input layer
(`docs/m2.5-input.md`), the focus graph (`docs/m2.5-focus.md`), the gamepad pump
(`docs/m2.5-gamepad.md`), the shells (`docs/m2.5-shells.md`), the hints
(`docs/m2.5-hints.md`), the remap UI (`docs/m2.5-remap.md`) and the console home
(`docs/m2.5-home.md`). Those gave the console shell one navigation model and a
start screen; this slice gives it a way to *type*, which a controller-only shell
otherwise cannot do.

## Why this slice exists

The plan's console-shell table (plan §7, *Console mode*) lists **Text entry** as
"in-app grid on-screen keyboard (bottom sheet) for search/rename, driven by the
same focus graph", and the compatibility table names it in v1 ("In-app grid
on-screen keyboard (search, rename, filters)"). A 10-foot shell must not ask
anyone to plug in a keyboard: search and profile renaming need a way to enter
text with a pad alone. The remap slice had already flagged the cost of the gap —
the Controls screen's deadzone/repeat numbers are real fields the pad cannot
type, so tuning stayed pointer-only "until the OSK slice".

It is hardware-independent (the same fixture Steam root the other smoke runs
used), so it ships while the M0 hardware closer waits on machine access.

## What ships

### `crates/input/src/osk.rs` — the model, framework-free and unit-tested

The module owns every editing rule, so the renderer stays a thin seam and the
layout/typing/caret arithmetic is tested without a webview, exactly like
`crate::focus` and `crate::grid`.

- **`OskLayer::{Letters, Symbols}`** — two character layers with the **same
  ragged row shape** (`["1234567890", "qwertyuiop", "asdfghjkl", "zxcvbnm,.-"]`
  and `["!@#$%^&*()", "[]{}<>/\\|=", ";:'\"`~?!,", "_+-*&%$#@!"]`), so switching
  layers keeps the focus index meaningful instead of jumping to the first key.
- **`OskKey`** — `Char { normal, shifted }` plus `Shift`, `Layer`, `Space`,
  `Backspace`, `CaretLeft`, `CaretRight`, `Clear`, `Done`. `OskKey::caption`
  takes shift and layer as *arguments* rather than reading state, so a key's
  label can never disagree with what pressing it does; `inserts(shift)` is the
  character a char/space key writes.
- **`OnScreenKeyboard`** — the text, a **character** caret (`0..=chars().count()`,
  so a non-ASCII title is never split), the `MAX_TEXT = 64` cap, shift, layer and
  the focused flat key index. `new`/`with_text`, `text`/`caret`/`split_at_caret`
  (for drawing the caret between two spans), `rows`/`key_count`/`key_at`/
  `focused_key`, `set_focus`, `limit`.
- **`graph()`** builds the `FocusGraph` over the ragged grid with ids equal to
  the flat key indices, so `focused_index` doubles as the key the view rings and
  the resolver's diagonal fallback + per-axis wrap keep a short row reachable
  from a long one (the model's own BFS test walks every key of both layers).
- **`handle(Action)`** is the whole input policy in one place: `Back` is always
  `Cancel` (a trapped sheet is worse than a lost edit), a direction moves the
  ring, `Confirm` presses the focused key.
- **`press_at(index)`** is the pointer path and the shared core: a char/space
  inserts at the caret and clears shift (shift is one character, like a phone
  keyboard), `Shift`/`Layer` toggle, the caret keys move, `Backspace`/`Clear`
  delete, `Done` returns `Submit`. `press_focused` focuses the first key instead
  of typing when nothing is focused, so a stray `Confirm` cannot type a `1` into
  an empty field.
- **`OskPress::{Idle, Edited, Submit, Cancel}`** — what one press did;
  `is_finished()` is `Submit | Cancel`.

### The keyboard's `Search` binding (`crates/input/src/map.rs`)

The keyboard layout now binds **`Key::F` to `Action::Search`** — the pad's
`North`/Y already was. `F` is "find"; while a text field has DOM focus the app's
pump yields every key to the field, so an `f` still types an `f` in the search
box. The hint row therefore grew an `F  Search` chip (its honesty test moved
from "the keyboard does not bind Search" to "it does").

### `crates/app/src/osk.rs` — the bottom sheet

`OskSheet` is a fixed overlay (`z-index:60`) with props `title`,
`keyboard: Signal<OnScreenKeyboard>`, `on_done: EventHandler<String>` and
`on_cancel: EventHandler<()>`. It draws the title, the text with a caret bar
between `split_at_caret`'s two spans, the resolved rows (each key's caption comes
from `caption(shift, layer)`, the focused key gets `focus::ring_style`), and a
Cancel button. A click calls `press_at`, so the pointer and the d-pad walk one
model; `Submit` calls `on_done` with the text, `Cancel` calls `on_cancel`.

`Done` does not write anything itself: the screen learns the text through
`on_done` and decides what it means. The model is **seeded with a copy** on open
(`with_text`), so a cancel discards the edit and leaves the screen's previous
text untouched.

### Wiring — the sheet is a per-screen overlay, not a route

Both screens keep their own `osk_open: Signal<bool>` and
`OnScreenKeyboard` signal and **intercept actions before their normal graph**:

- **Library search** (`crates/app/src/main.rs`). `Search` seeds the keyboard
  from the current filter and opens the sheet; while it is open the drain hands
  every action to `handle`. `Submit` calls the shared `commit_search` — it sets
  `query`, **clears the focus** (the new filter may not contain the focused
  card) and closes the sheet. Both the action drain and the sheet's pointer
  `on_done` commit through `commit_search`, so a controller and a mouse cannot
  leave the filter and the focus in different states. The sheet is rendered
  *outside* the scroll container, so the grid behind it never scrolls while
  typing.
- **Detail → new profile name** (`crates/app/src/detail.rs`). `Search` seeds the
  keyboard from the name field; `Submit` calls `create_profile`, which the
  pointer's **Save button also now calls** — the inline `spawn(async move { … })`
  that button used moved out to `create_profile`, so a controller cannot create a
  differently-shaped profile than a mouse. The name is trimmed inside
  `create_profile`; an empty or all-spaces name is ignored. `Done` clears the
  field and reloads the list exactly like Save, so the new profile becomes the
  active one.

## Verification

- `pitagames-input`: **93** tests (up from 74; **19** in `osk`), clippy
  `-D warnings` and `rustfmt` clean on macOS and in `archlinux:latest`. The new
  tests cover the ragged shape of both layers, the reachability BFS, the first
  navigation entering the first key, a direction moving one key and wrapping, a
  letter inserting and advancing the caret, shift upper-casing one character,
  shift turning the digit row into symbols, the symbol layer swapping captions
  while keeping the focus index, backspace before the caret, a non-ASCII
  character deleted as one, the caret keys editing in the middle, space/clear/
  done, the cap refusing an insertion but still submitting, `set_text`'s cap and
  caret, `handle`'s action mapping, `Confirm` without focus, pressing past the
  layout, the captions, and the graph ids being the flat key indices. The
  `map`/`hint` tests moved `F` to `Search`.
- `crates/app`: **169** tests (unchanged — the sheet is a pure render seam with
  no model of its own, and its model is tested in `pitagames-input`), clippy
  `-D warnings` and `fmt --check` clean in `archlinux:latest`; the pure crates
  pass on macOS.
- **Xvfb smoke run in `archlinux:latest`** against a six-game fixture Steam root,
  desktop shell (the keyboard walks the sheet, a click would walk the same one):
  - `f` opens the sheet on the grid; `Return` focuses `1`, directions reach `c`
    and `e`, and `Done` commits the filter — the real search box then reads `ce`
    and the grid shows only Celeste, with the focus ring cleared;
  - reopening seeds the sheet with `ce` (not an empty box), and `Esc` cancels
    without touching the filter;
  - on the detail page, `f` opens a **New profile name** sheet, directions type
    `abc`, `Done` closes it and the profile appears in the Profiles list as
    **ACTIVE** (SQLite holds `('steam', '504230', 'abc')`), exactly the result
    the Save button gives;
  - the **console shell** (`--console`) draws the same sheet over the Library
    screen at the bigger 10-foot type. Screenshots in `target/smoke/run/` and
    `target/smoke/console/`; the scripts are `target/smoke/osk-smoke.sh` and
    `target/smoke/osk-console-smoke.sh`.

## Known limits

- **No OSK entry point from the console home.** The sheet lives on the Library
  (search) and the detail page (rename); the console shell opens on `Home`, whose
  only text surface is the same top-right search box the Library borrows. A couch
  user reaches search by pressing the Library tab first. The console home's own
  search/rename is part of the later *console library grid + overlay* item.
- **The sheet is not a general text field.** It types into one screen-owned
  buffer (the filter, the profile name) and cannot edit the Controls screen's
  numeric fields yet, which the remap slice left pointer-only.
- **No physical-keyboard typing on the sheet.** With the sheet open the app's
  pump hands *actions* to `handle`, so the letters type nothing and `f` is the
  pump's `Search`, which is a no-op while the sheet is already open. A desktop
  user types in the real search box; the on-screen keyboard is the pad's path.
- **No pointer-focused sheet.** The sheet has no popup/focus trap of its own; it
  is only opened by an `Action`, and the ring is the model's focus.
- **Reachability is per-layer and wrap-only at the edges.** The resolver's
  diagonal fallback keeps every key reachable (tested), but a ragged row means a
  direction can land on a *different column than expected* — the smoke run's
  script had to count rows, which a person does by eye.
- **Not driven against a real controller or a TV.** The pad half is covered only
  by the pump's `ReplaySource` tests and the shared `Action` path; no TV is
  attached to either machine.
