# M2.5 — safe mode and the window watchdog (`crates/app/src/safe_mode.rs` + `crates/app/src/supervisor.rs`)

Status: implemented; `crates/app` builds, lints and tests in `archlinux:latest`
(**204** tests) and an Xvfb smoke run in the same container rendered the window
in safe mode (DMABUF renderer off, a `Safe mode` badge in the header) and
exercised the automatic retry with a simulated webview init failure. Nothing
here has met a real GPU that cannot composite.

## Why this slice exists

The plan's last M2.5 items are `--safe-mode` and the 10-foot pass. Safe mode is
the escape hatch the plan calls out under *Safe mode* (plan §7) and
`AGENTS.md`:

> `--safe-mode` disables the DMABUF renderer, animations and blur; webview init
> failure must auto-retry into it. A black screen with no keyboard is
> unacceptable.

The RX 9070 composites through WebKitGTK's DMABUF renderer by default — the fast
path — but a driver that does not support it can leave the webview black. A
window the user cannot see is a window the user cannot close, so there has to be
a way in that does not need the GPU, and a way to *reach* it without the user
knowing the flag exists.

It is hardware-independent to build, so it ships while the M0 hardware closer
waits on machine access.

## What ships

### `crates/app/src/safe_mode.rs` — the switch, framework-free

The module owns the environment names and the pure decision:

- **Three ways in, all ORed** by `enabled(flag, configured)` /
  `enabled_from(flag, configured, env)`:
  `--safe-mode` (this run), `[ui] safe_mode = true` in `config.toml` (sticks),
  and `PITAGAMES_SAFE_MODE=1` (what the supervisor sets when it retries).
- **`apply_webkit_env()`** sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` before the
  webview is created. It is the one place the launcher mutates its own
  environment (documented `unsafe`).
- **`CHILD_ENV` / `READY_FILE_ENV`** are the supervisor's handshake; **`is_child`,
  `ready_path`, `fake_webview_failure`** read them.

Safe mode also forces `DisplayConfig.reduce_animations`, so the shell cannot
re-enable motion by accident.

### `crates/app/src/supervisor.rs` — the process that owns the launcher

The GUI cannot restart itself after its webview fails: GTK/WebKit will not
initialize again in the same process, and a failed init can abort rather than
unwind. So the launcher runs **two roles**:

- the **supervisor** — what the user or the `.desktop` file starts — takes the
  single-instance lock, then spawns the **GUI child** and waits;
- the **GUI child** (`PITAGAMES_GUI_CHILD=1`) builds the webview and, once its
  first render is up, writes the ready file the supervisor passed it via
  `PITAGAMES_READY_FILE`.

The child writes that file from `App`'s first render (`use_hook`), which is only
reached after the webview initialized. Two behaviours fall out:

- **Safe-mode auto-retry.** A child that dies *before* it is ready failed to
  start — the DMABUF path — so `decide` returns `RetrySafe`, the supervisor sets
  `PITAGAMES_SAFE_MODE=1` and starts the child again. Only if *that* fails does
  it give up.
- **Window watchdog.** A child that crashes *after* it was ready is restarted,
  bounded by `MAX_RESTARTS = 3`, so a transient compositor crash does not end the
  session and a crash loop cannot spin forever.

`decide(safe, ready, exit, restarts)` is pure and table-tested; `run` is the
`Command::spawn`/`wait` loop around it. A clean exit before ready is `Done` (the
app chose to stop), never a retry.

### The startup split (`crates/app/src/main.rs`)

- `main` parses args, handles `--version`, and — if it is the child — calls
  `run_gui` and returns.
- The **supervisor** path reads `config.toml` (for `safe_mode`), prints the
  config warnings once, takes the instance lock, and calls `supervisor::run`.
- `run_gui` resolves safe mode, applies the WebKit switch, forces
  `reduce_animations`, starts the **activation socket** (the child owns the
  window, so a second launch raises *this* process), ensures the menu entry, and
  launches Dioxus.

The lock and the socket deliberately live in different roles: the supervisor
holds the lock for the whole run, the child listens for "focus me".

### CSS and the badge

The motion half of safe mode is **enforced by construction, not by a
stylesheet**. The original design emitted one global rule
(`animation:none; transition:none; scroll-behavior:auto; backdrop-filter:none`)
as a `<style>` element, but the M2.5 design pass proved with an Xvfb probe that
this Dioxus build **ignores a `<style>` element written in RSX** (a
`div{background:#ff00ff}` rule never painted) and that injecting CSS would need
JavaScript, which the renderer boundary forbids. So the rule was removed rather
than shipped dead, and the app now simply contains no motion: no `animation`,
`transition`, `backdrop-filter` or `scroll-behavior` with a live value anywhere
in `crates/app/src`, kept that way by the `no_screen_ships_motion` test
(`docs/m2.5-design.md`, ADR-0028). `reduce_animations` therefore changes nothing
in CSS today — there is nothing to switch off — and safe mode's real work is the
DMABUF renderer, the supervisor/retry and the `Safe mode` chip (which shows so a
couch user knows why the UI looks different, with a title explaining how to
leave it).

### The test hook

`PITAGAMES_FAKE_WEBVIEW_FAILURE=1` makes the GUI child exit before its first
render, but only when safe mode is *off* — so attempt one crashes and attempt
two (safe) succeeds. It is the only way to exercise the retry without a broken
GPU, and the CI smoke run is its one caller.

## Verification

- `crates/app` gained **13** tests (191 → **204**): 2 `shell` (the flag is
  recognised; the motion guarantee is the source guard described above) + 4 `safe_mode` (the three
  switches OR together; a falsy environment value does not; the WebKit name; the
  truthiness rule) + 7 `supervisor` (clean exit is Done; crash-before-ready
  retries; crash-before-ready in safe mode gives up; a clean early exit is Done;
  a ready crash restarts until the cap; a signal counts as a crash; the ready
  file is named for the process).
- `pitagames-core` stays at **97** (the `safe_mode` field was added to `UiConfig`
  and the defaults/round-trip tests assert it); `pitagames-input` is unchanged.
- `cargo clippy -p pitagames --all-targets -- -D warnings` and `cargo fmt
  --check` are clean in `archlinux:latest`; the pure crates pass on macOS.
- **Xvfb smoke run in `archlinux:latest`** (script `target-arch/safe-mode-smoke.sh`):
  `pitagames --safe-mode` under `dbus-run-session` + `Xvfb` rendered the window
  with the `Safe mode` chip and the stderr notice; and
  `PITAGAMES_FAKE_WEBVIEW_FAILURE=1 pitagames` logged the simulated failure
  (`[pitagames] test hook: simulating a webview init failure`), then the retry
  line (`[pitagames] the window did not start; retrying in safe mode …`), then
  `[pitagames] safe mode: DMABUF renderer disabled …` and rendered the window —
  proving the auto-retry. Screenshots in `target-arch/safe-mode-*.png`.

## Known limits

- **Only a crashing webview is detected.** A renderer that initializes and then
  paints nothing (a silent failure) is not a crash, so the retry does not fire;
  the user still has to pass `--safe-mode` by hand. The ready file is written on
  the first render, which a DMABUF *init* failure never reaches, but a
  *compositing* failure can.
- **The watchdog restarts in the same mode.** A crash loop restarts identically
  up to the cap before giving up; it does not escalate to safe mode. (Safe mode
  remains the manual recovery.)
- **No Settings screen yet.** `[ui] safe_mode` in `config.toml` is the persisted
  toggle; the plan's "keep it in Settings" wants a screen that M3/M4 owns.
  `--safe-mode` is a one-run override and is not written back.
- **The supervisor is always a child process.** The GUI is never PID 1 of the
  launcher: the lock, the crash watchdog and the retry need a parent. A `SIGKILL`
  of the supervisor orphans the child, which then exits with its window.
- **The test hook ships.** `PITAGAMES_FAKE_WEBVIEW_FAILURE` is a documented,
  harmless switch (it only forces the retry path); it costs a few bytes and buys
  a reproducible CI check.
- **Not validated on hardware.** No machine in-house currently fails DMABUF, so
  the retry is proven with the hook and the model tests, not a real GPU crash.
