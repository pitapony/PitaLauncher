# M2.5 — the console overlay (`crates/app/src/overlay.rs`)

Status: implemented; `crates/app` builds, lints and tests in `archlinux:latest`
(**191** tests) and an Xvfb smoke run in the same container opened the overlay
from the keyboard, walked its rows (disabled power placeholders included), added
the game rows when a game was open and switched the shell from inside it. Nothing
here has met a real controller or a TV.

This is the twelfth M2.5 slice, on top of the input layer
(`docs/m2.5-input.md`), the focus graph (`docs/m2.5-focus.md`), the gamepad pump
(`docs/m2.5-gamepad.md`), the shells (`docs/m2.5-shells.md`), the hints
(`docs/m2.5-hints.md`), the remap UI (`docs/m2.5-remap.md`), the console home
(`docs/m2.5-home.md`), the on-screen keyboard (`docs/m2.5-osk.md`) and the launch
hand-off (`docs/m2.5-handoff.md`). Those built the couch shell and its
navigation and made it step aside for a game; this slice adds the **system menu**
the plan calls the console *Overlay* — the one surface that is not a screen.

## Why this slice exists

The plan's console-shell table (plan §7, *Console mode*) lists **Overlay** as:

> `Guide`/`Start`: resume, graphics, store page, power (suspend/restart/shutdown),
> exit console mode, controller + battery status, clock.

and the M2.5 checklist carries it as part of "Console library grid + filters +
game page + overlay". Without it a couch user has a Play button and nothing else:
no way to see which controller is connected, what the time is, or to leave the
console shell from the pad. The overlay is that menu.

It is hardware-independent, so it ships while the M0 hardware closer waits on
machine access.

## What ships

### `crates/app/src/overlay.rs` — the model, framework-free and unit-tested

The module owns *what rows exist* and *which one is focused*; `App` owns the
signal that says the overlay is open, the window/`spawn` calls a choice makes and
the pads and batteries it names. It is tested without a webview, exactly like
`crate::handoff`, `crate::home` and `crate::grid`.

- **`OverlayChoice::{Close, Details, StorePage, ToggleShell}`** — one thing the
  overlay can do. `Details` opens the running (or last opened) game's detail page,
  `StorePage` asks Steam to open its store page, `ToggleShell` switches between
  the two shells.
- **`OverlayContext { console, game }`** — what the shell is doing when the menu
  opens. The rows are built from it every time, so a row is never offered for a
  game that is not there.
- **`OverlayEntry { label, detail, choice }`** — one row. `choice: None` is a
  **disabled** row: `is_enabled()` is what the view greys it with.
- **`Overlay::build(context)`** — the rows, top to bottom:
  1. **Resume** — always; closes the menu.
  2. **Game details** — only with a game in context (the running one, else the
     detail page's). The plan calls this "graphics"; there is no separate
     Graphics screen until M3, so it lands on the detail page's Runtime panel.
  3. **Store page** — only for a Steam game (Steam owns the store page).
  4. **Exit console mode** / **Enter console mode** — the label follows the shell.
  5. **Suspend / Restart / Shut down** — the plan's power menu, **shown but
     disabled**: power is the console session's (v1.1, over logind), and a
     controller user should see the row rather than wonder where it went.
- **`format_clock(now)` / `now_local()`** — the `HH:MM` clock. The offset comes
  from `localtime_r` rather than `time`'s `local-offset` feature, because the app
  is multithreaded where that feature is unsound; `localtime_r` only reads `TZ`.
- **`move_focus(action)`** — walks the rows with the shared `FocusGraph` in a
  single column, so `Down` past the last row wraps back to `Resume` and a menu is
  a loop, never a trap.

### The view (`crates/app/src/overlay_view.rs`)

`OverlayView` is a fixed, full-window backdrop (`z-index:100`) with a centred
panel: a `Menu` title and the clock, one row per entry (the focused row ringed
with `focus::ring_style`, a disabled row greyed and non-clickable), and the
controller + battery line with a "M or Start closes" hint. A pointer click takes
the same `apply_overlay_choice` path the d-pad does, so mouse and controller
cannot drift.

It is an **overlay, not a route**: the screen beneath keeps its focus and its
scroll position.

### Wiring (`crates/app/src/main.rs`)

- `App` holds `overlay: Signal<Option<Overlay>>` (`None` is closed),
  `batteries: Signal<BTreeMap<DeviceId, Battery>>` and a `clock: Signal<String>`.
- The **pad drain and the keyboard pump** intercept `Action::Menu` before the
  screen dispatch and open the overlay; while it is open they route **every**
  action into `apply_overlay` (navigation moves the ring, `Confirm` runs the row,
  `Back`/`Menu`/`Guide` close). This is checked before the keyboard's text-field
  yield, so a stray focus cannot half-trap the menu.
- **`open_overlay`** builds the context from the running game (the play slot)
  else the open detail page's game, looked up in the library for its title and
  store.
- **`apply_overlay_choice`** performs a choice: `Details` records the current view
  as Back and opens the detail page; `StorePage` calls
  `library::spawn_store_page` (`core::launch::steam_store` → `steam
  steam://store/<appid>`); `ToggleShell` calls the existing `toggle_shell`.
- A **gamepad worker** now reports `GamepadEvent::Battery` (a `Battery` change,
  once), because `gilrs` has no battery event and the worker has to poll; the app
  folds it into `batteries`, and `overlay_status` pairs the last pad's name with
  its charge for the panel's controller line.
- A **timer future** refreshes the clock every 20 s, only while the menu is open
  (so a closed overlay never re-renders for a minute change).
- The play drain **closes the overlay on `Started`**, so a game that starts owns
  the screen and the menu does not sit over it.
- The keyboard layout gained **`Key::M` bound to `Action::Menu`** (the pad's
  `Start`), so a keyboard-only desktop can reach the menu too; `focus::key_from_tao`
  translates it and the hint row names it.

### `crates/core/src/launch.rs` — `steam_store(app_id)`

A `LaunchSpec` for `steam steam://store/<appid>`, argv-only like the run and
install helpers, with `app::library::spawn_store_page` as the caller.

## Verification

- `crates/app` gained **9** `overlay` tests and **1** `gamepad` battery test
  (181 → **191**): Resume is always first and focused, a Steam game adds details
  and a store page, a non-Steam game has no store page, a game-less overlay has no
  details, the shell row follows the shell, the power rows are shown but disabled,
  navigation moves the ring and wraps both ways, a disabled row offers no choice,
  the clock is padded, and a battery change is readable from the pump.
- `pitagames-input` is unchanged at **93** tests (the `Key::M` → `Menu` binding
  updated the keyboard `map` tests and the hint row test now names `M`/`Menu`
  instead of skipping it); `pitagames-core` is **97** with the `steam_store` test.
- `cargo clippy -p pitagames --all-targets -- -D warnings` and `cargo fmt --all
  -- --check` are clean in `archlinux:latest`; the pure crates pass on macOS.
- **Xvfb smoke run in `archlinux:latest`** (`--console`, one seeded Steam game,
  script `target-arch/overlay-smoke.sh`):
  - `m` opened the menu over the console home: **Resume** ringed, `Exit console
    mode`, then `Suspend`/`Restart`/`Shut down` greyed with "arrives with the
    console session", and the footer read `Controller: Keyboard`;
  - `Down` twice moved the ring to the disabled `Suspend` row;
  - `Escape` closed it and the home was unchanged;
  - opening a game (two `Down`s to a shelf tile, `Enter`) and pressing `m` again
    added **Game details** ("Portal 2 · play, profiles and runtime") and **Store
    page** ("Open in Steam") above `Exit console mode`;
  - `Down` to `Exit console mode` and `Enter` flipped the header from `CONSOLE`
    to `DESKTOP` and left the detail page open, exactly as `toggle_shell`
    documents.
  - Screenshots land in `target-arch/overlay-*.png`.

## Known limits

- **The power rows are placeholders.** Nothing runs on `Suspend`/`Restart`/`Shut
  down`: the plan puts the power menu in the console session (v1.1, over logind
  with `zbus`/polkit), and a half-implemented shell-out here would be worse than a
  visible "arrives with the console session".
- **`Game details` lands on the detail page, not a Graphics screen.** There is no
  separate graphics screen until M3, so the button opens the page whose Runtime
  panel already edits the profile. The plan's overlay wording ("graphics") is the
  M3 shape.
- **Battery is best-effort.** `gilrs` has no battery event, so the worker polls
  `power_info` and reports a change once; a pad that has never reported power
  shows its name alone, and a wired pad is indistinguishable from an unknown one
  in the line.
- **The clock is local time read each tick.** The container's timezone is UTC, so
  the smoke run could not show a non-zero offset; the `localtime_r` path is the
  only one exercised.
- **The overlay opens on `Menu`, not `Guide`.** The shipped `Guide`/`F11`
  behaviour (toggle the shell) is preserved, and the overlay carries an explicit
  "Exit console mode" row, so the plan's "`Guide`/`Start`" is honoured through
  `Start` (the keyboard's `M`). Moving `Guide` to open the overlay would have
  broken the documented, smoke-tested shell toggle.
- **The menu is one flat column.** No sections, no submenus, no scrolling past
  the viewport (the row count is small and fixed).
- **No pointer hover, no focus trap beyond the modal backdrop.** The backdrop
  swallows clicks and the pumps route every action into the menu, but Tab/DOM
  focus is not part of navigation anywhere in the launcher.
- **Not driven against a real controller or a TV.** The battery line, the clock
  and the row set are covered by model tests and the keyboard smoke run only.
