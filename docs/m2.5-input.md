# M2.5 — the input layer (`crates/input`)

Status: `pitagames-input` is implemented and verified with its own test suite on
macOS and in `archlinux:latest`. It has **no consumer yet** — the focus graph,
the two shells and the controller remapping UI that read it are the next M2.5
slices, exactly like `stores::queue` shipped before the GUI install flow drove
it. Nothing here has been exercised against a real controller on the target
machines.

## Why this slice exists

M2.5 makes the same app a controller-only, fullscreen 10-foot shell. The plan's
first item is the input crate, for three reasons:

1. **One input path for both shells.** The desktop shell and the console shell
   must react to the same *actions*, not to the same buttons: `Confirm` is `A`
   on a pad, `Enter` or `Space` on a keyboard, and the focus graph only ever sees
   `Confirm`. A close, shared action set is what makes a controller-only shell
   completable.
2. **A testable core.** Button glyphs, deadzones and repeat timing are exactly
   the kind of logic that is painful to verify through a webview. Here it is a
   pure state machine fed raw events and an explicit clock, so every rule has a
   unit test that never sleeps and never needs a device.
3. **The renderer boundary again.** `input` sits below `app` and contains no
   Dioxus types, so the focus graph and the shells can be built on top of it and
   later ported to a native renderer with the rest of the UI.

## What the plan rule fixes

- **No `navigator.getGamepads()`.** WebKitGTK does expose it (through
  `libmanette`), but it only reports while the webview has focus, carries no
  remap or hotplug metadata, and cannot be exercised headlessly. Every device
  event comes from `gilrs` over evdev.
- **Time is injected, not read.** `Input::handle(event, now)` and
  `Input::tick(now)` take an `Instant`; the shell owns the tick. That is what
  lets the repeat rules be tested at 399 ms and 400 ms without a `sleep`, and it
  keeps the input layer independent of any event-loop framework.

## Layers

| Module | Role |
|---|---|
| `action` | `Action` (the closed action set), `ActionKind`, `ActionEvent` |
| `binding` | `Button`, `Axis`, `Stick`, `Direction`, `Key`, `Binding` |
| `map` | `InputMap` (bindings + deadzone + repeat), `InputMaps` (the file) |
| `source` | `RawEvent`, `Device`, `DeviceId`, `Battery`, `InputSource` |
| `gamepad` | `GilrsSource` — the only place that touches `gilrs` |
| `replay` | `ReplaySource` — a scripted source for tests and fixtures |
| `mapper` | `Input` — the state machine that emits `ActionEvent`s |

The data flows one way: a source yields `RawEvent`s, `Input` folds them through
the device's `InputMap`, and the shell acts on `ActionEvent`s. Nothing below
`app` knows what a shell looks like.

## Actions

`Action` is deliberately small and closed:

```text
navigate_up  navigate_down  navigate_left  navigate_right
confirm      back           context        search
menu         guide          tab_next       tab_prev
```

`Action::ALL` is the single list the remap UI and the config file both iterate,
so a new action cannot be forgotten in one place. `Action::repeats()` is the
policy — only movement and tab switching repeat; holding `Back` or `Confirm`
must stay one action, or a stuck button would walk back through a stack of
screens.

## Bindings and the two defaults

A `Binding` is one physical control:

| Binding | Reads |
|---|---|
| `Button { button }` | a gamepad button is held |
| `Key { key }` | a keyboard key is held |
| `Axis { axis, positive }` | a single axis (a trigger, or a d-pad reported as axes) is past the deadzone in one direction |
| `Stick { stick, direction }` | an analog stick is pushed toward a direction |

Each action holds a **list** of bindings, so the d-pad and the left stick both
drive `NavigateUp`. The built-in layouts:

- **Gamepad** (`InputMap::gamepad`): d-pad and left stick move focus, `South` is
  Confirm, `East` Back, `West` Context, `North` Search, `Start` Menu, `Mode`
  Guide, the bumpers switch tabs.
- **Keyboard** (`InputMap::keyboard`): arrows and WASD move focus, `Enter`/`Space`
  confirm, `Esc` goes back, `Tab`/`E` and `Q` switch tabs.

A key binding is only ever read from the keyboard and a controller binding only
from a gamepad (see `binding_active`), so a stray `Key` in a pad's map cannot be
pressed by the keyboard acting as that pad.

### The L1/L2 naming trap

`gilrs`'s `Button::LeftTrigger` is SDL's `leftshoulder` (the bumper) and
`gilrs::Button::LeftTrigger2` is SDL's `lefttrigger` (the analog trigger) — the
opposite of what the names suggest. Our `Button` uses the SDL reading and
`GilrsSource` resolves the swap once, with a test that asserts it, so the rest of
the codebase never has to think about it.

## The state machine

`Input` tracks, per origin (the keyboard, or one gamepad session):

- which buttons are down and the last value of every axis;
- which bindings of that origin are currently satisfied;
- which actions are held and by how many sources.

On every event it recomputes the origin's contribution and diffs it against the
active set:

- an action with no sources becomes active → `Pressed`;
- an action that loses its last source → `Released`;
- an action held by two sources (pad *and* keyboard) stays held when one lets go.

A single event can both start one action and end another — a stick push changes
the dominant axis — so **releases are reported before presses**: a caller walking
a focus graph sees the old direction let go before the new one is taken.

### Deadzone and direction

The sticks use a **radial** deadzone (`InputMap::deadzone`, default `0.35`)
applied to the stick as a whole, and then the dominant axis wins, so a diagonal
push moves one cell rather than two. Positive `Y` is down, matching SDL and
`gilrs`. Single-axis bindings (`Axis`) compare that axis' value against the same
deadzone; a trigger binding usually wants a lower one, since a trigger's whole
range is `0.0..=1.0`.

### Repeat

A held direction schedules its first repeat at `repeat_delay_ms` (default `400`)
after the press and then one every `repeat_interval_ms` (default `80`) from
`tick`. The interval is copied into the hold at press time, so `tick` never has
to look the map up again and a remap mid-hold cannot change a running timer.

### Devices

- **Identity is the GUID, not the session id.** A `DeviceId` is gilrs' session
  numbering; a `Device` carries its SDL GUID and `InputMap`s are keyed by the
  GUID, so a remap survives a reconnect. A test replugs a pad under a new id and
  checks the remap still applies.
- **Hotplug releases cleanly.** A disconnect drops the pad's state and releases
  every action it was holding.
- **Battery is polled.** `gilrs` reports power by polling, not as an event, so
  `GilrsSource::poll` diffs `power_info()` for each connected pad and emits a
  `RawEvent::Battery` on a real change (the first `Unknown` is dropped as noise).

## Persistence

`InputMaps` holds only overrides and round-trips through TOML at
`<XDG_CONFIG_HOME>/pitagames/input.toml`
(`core::paths::input_maps_file`). A missing file is the normal state and means
"use the defaults". A hand-edited file is validated (deadzone within `0.0..=1.0`,
a non-zero repeat interval), and `save` writes a sibling `.toml.tmp` and renames
it, so a crash cannot leave a half-written file.

The maps are their own file rather than a section of a future `config.toml`
because a device GUID is an awkward table key and because the file is owned
entirely by this crate; when `config.toml` lands it can absorb the path.

## What is _not_ here yet

- **The focus graph** (`use_focus(id, row, col)`, the spatial resolver, per-axis
  wrap, scroll-into-view, the focus ring) is the next M2.5 slice; this crate only
  produces the actions it consumes.
- **The shells** (`Shell::{Desktop, Console}`, `--console`, `StartMode`,
  `F11`/`Guide` toggling) and the remapping UI.
- **No consumer.** `crates/app` does not depend on `pitagames-input` yet, so the
  whole thing is covered by its own tests and nothing else.

## Verification

39 unit tests in `pitagames-input`:

- every action round-trips through its wire name; only movement repeats; wire
  names stay TOML-key safe;
- each binding shape round-trips through TOML; every button is listed once;
- a device with no override falls back to its kind; an override replaces the
  default; maps round-trip through TOML; a hand-edited file is validated; a
  missing file is an empty set and a save round-trips without a temp file;
- a button press/release is one action; an unbound button does nothing; the
  d-pad and the stick both move focus; the radial deadzone ignores small
  movements and a diagonal can clear it; a diagonal push moves one direction;
- a held direction repeats after the delay then on the interval; a
  non-repeating action never repeats; the keyboard drives the same actions and
  two bindings keep an action held until the last is released; an axis binding
  reads a trigger; only the keyboard answers key bindings; a keyboard key does
  not disturb a pad hold;
- disconnecting a pad releases what it held; a reconnect keeps the remap by GUID;
  events for an unknown pad are ignored; a battery change is remembered; the last
  input follows the device; replacing the maps drops hold state;
- the gilrs conversion: the shoulder/trigger swap, the axis names, the power
  states and a UUID becoming its hex GUID.

`cargo test -p pitagames-input`, `cargo clippy -p pitagames-input --all-targets
-- -D warnings` and `cargo fmt --all -- --check` are clean on macOS and in
`archlinux:latest` (where `gilrs` builds against `systemd-libs`/`libudev`). The
crate is added to the CI core job, which installs `libudev-dev` on the Ubuntu
runner.
