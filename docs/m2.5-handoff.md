# M2.5 — the launch hand-off (`crates/app/src/handoff.rs`)

Status: implemented; `crates/app` builds, lints and tests in `archlinux:latest`
(**181** tests) and an Xvfb smoke run in the same container played a seeded
non-Steam game in the console shell: the window unmapped while it ran and mapped
again when it ended, with the session written to the history and the playtime
summed. Nothing here has met a real controller, a real store game or a TV.

This is the tenth M2.5 slice, on top of the input layer
(`docs/m2.5-input.md`), the focus graph (`docs/m2.5-focus.md`), the gamepad pump
(`docs/m2.5-gamepad.md`), the shells (`docs/m2.5-shells.md`), the hints
(`docs/m2.5-hints.md`), the remap UI (`docs/m2.5-remap.md`), the console home
(`docs/m2.5-home.md`) and the on-screen keyboard (`docs/m2.5-osk.md`). Those
built the couch shell and its navigation; this slice makes it **get out of the
way while a game runs and come back when it ends** — the last leg of the M2.5
exit criterion ("launch it, quit it and land back in console mode").

## Why this slice exists

The plan's console-shell table (plan §7, *Console mode*) lists **Handoff** as:

> Launch hides the window and pauses the input pump; on game exit the window is
> shown and focus requested via an activation token. If the compositor refuses,
> a "game exited — press Guide" badge shows on next focus.

and the risk table names the reason the fallback is not optional:

> Wayland won't let a background app raise itself after a game exits |
> Activation token + `request_user_attention`; visible "game exited — press
> Guide" badge as fallback; session mode removes the problem because the
> launcher owns the compositor.

Without it, a couch user presses Play and watches the launcher sit on top of (or
behind) the game, and when the game exits nothing pulls the launcher back — a
black screen and a controller that does nothing, exactly the failure mode
`--safe-mode` exists to avoid.

It is hardware-independent, so it ships while the M0 hardware closer waits on
machine access.

## What ships

### `crates/app/src/handoff.rs` — the model, framework-free and unit-tested

The module owns the *decisions*; `App` owns the window calls and the clock, so
the state machine is tested without a webview, exactly like `crate::focus` and
`crate::grid`.

- **`WindowAction::{Hide, Show, None}`** — what to do to the window for one
  transition. The model cannot touch a window, so it returns the decision and
  the app applies it (`shell::hide_window` / `shell::show_and_focus`).
- **`Handoff::started(id, console)`** — the game started. Always claims the slot,
  but returns `Hide` **only for the console shell**: the desktop shell keeps its
  window so a pointer user can keep browsing while a game runs, and its "end"
  transition is a no-op.
- **`Handoff::ended(title, summary)`** — the game ended. Returns `Show` only if
  the window was actually hidden (so a desktop session, or an end without a
  start, leaves it alone), arms `awaiting_focus`, and builds the fallback badge
  from the verdict.
- **`focus_granted()`** — a real `Focused(true)` event: cancels the pending
  fallback *and* clears a badge already on screen (the user got the window back).
- **`focus_timeout()`** — no focus within `FOCUS_GRACE` (2 s): promotes the
  pending badge to the shown one.
- **`dismiss()`** — the player pressed Guide (or clicked Dismiss).
- **`badge_text(title, summary)`** — the one sentence (`"Gizmo exited 0 after 5s
  — press Guide to return."`), built in one place so the text a controller shows
  and the text a test asserts cannot drift.
- **`hidden()`** is also the input pause: while the window is hidden the game
  owns the pad and the keyboard, and a hidden window must not accumulate focus
  moves behind it.

### The window seam (`crates/app/src/shell.rs`)

- **`hide_window()`** — `Window::set_visible(false)`.
- **`show_and_focus()`** — unminimize, map and focus. Extracted so
  `app::activation::raise_window` (a second launch asking for focus) and the
  hand-off's return share one implementation.
- **`request_attention()`** — `Window::request_user_attention(Critical)`, the
  taskbar nudge when the compositor would not focus the window.
- **`install_window()` / `reveal_window()`** — a `OnceLock<Arc<tao::Window>>`
  recorded once in `App`, and a thread-safe "map and focus" the game's worker
  calls. This is the one non-obvious piece: see below.

### The WebKitGTK trap (why the return trip is not a future)

The obvious implementation — hide the window from the play drain, show it from
the same drain when `Finished` arrives — **does not work**, and the container is
what showed it. Once the app hid the window, the game's `Finished` report sat in
the channel forever; the session was never recorded and the window never came
back.

The cause is in `dioxus-desktop`'s render loop. `WebView::poll_vdom` bails out
early when a previous render's edits have not been flushed by the webview:

```rust
let edits_flushed_poll = self.edits.wry_queue.poll_edits_flushed(&mut cx);
if edits_flushed_poll.is_pending() {
    return;                      // never reaches dom.wait_for_work()
}
```

An **unmapped** WebKitGTK window stops running its render loop, so the flush
never completes, so the virtualdom is never polled again — including the future
that would map the window. A launcher that hides itself could never wake up.

The fix keeps the unmap (the plan asks for a hidden window) and moves the
unfreeze off the event loop: `tao::Window: Send + Sync` on Linux, and every tao
window call is a request queued to the event loop rather than an X call, so the
game's worker thread can map the window. `play::spawn`'s thread calls
`shell::reveal_window()` **before** it sends `PlayEvent::Finished`, which maps
the window, which lets the webview flush, which wakes the virtualdom, which then
processes the queued `Finished` and runs the rest of the drain.

A minimized window is *not* a workaround: on a real window manager minimize
iconifies (unmaps) the window and hits the same freeze — it only looked alive in
the container because Xvfb has no window manager at all.

### Wiring (`crates/app/src/main.rs`, `crates/app/src/play.rs`)

- `App` holds `handoff: Signal<Handoff>` and `handoff_deadline:
  Rc<Cell<Option<Instant>>>` (a plain `Cell`, so waiting on it never
  re-renders).
- The **play drain** matches `Started` (→ `begin_handoff`) and `Finished` (→
  `end_handoff`, then the history row and playtime as before). A stale event for
  a game that no longer holds the slot is ignored, exactly as before.
- **`begin_handoff`** asks the model (with `shell.shell().is_console()`), hides
  the window and logs `stepping aside while <id> runs`.
- **`end_handoff`** asks the model with the last verdict, shows and focuses the
  window, arms the focus deadline and logs `<title> ended; asking for focus`.
- A second **`use_wry_event_handler`** watches `WindowEvent::Focused(true)`: a
  confirmed focus cancels the fallback and clears a badge; a focus event with
  nothing pending (the first focus at startup) is a no-op.
- A **timer future** polls the deadline every 250 ms; when it passes with focus
  still unconfirmed it calls `shell::request_attention()`, promotes the badge and
  logs `the window did not take focus; showing the badge`.
- The **pad and keyboard pumps** drop every action while `handoff.hidden()`, so
  the game owns the controls and the hidden window accumulates no focus moves.
- **`guide_action`** is `Guide`'s app-level job: if the badge is showing, the
  first press dismisses it; otherwise it toggles the shell as before. So the
  badge's "press Guide to return" is literally true.
- The badge renders as its own strip under the notice line, with a Dismiss
  button for pointer users.

## Verification

- `crates/app` gained **12** `handoff` tests (169 → **181**): the console shell
  hides and the desktop shell does not, a hidden window returns when the game
  ends, a desktop session and an end-without-a-start are no-ops, a granted focus
  clears the pending fallback and a shown badge, a refused focus promotes the
  badge, the badge names the verdict and survives a blank one, dismissing clears
  it, a new launch clears a stale badge, and a timeout while the game is still
  running does nothing.
- `cargo clippy -p pitagames --all-targets -- -D warnings` and `cargo fmt --all
  -- --check` are clean in `archlinux:latest`; the pure crates pass on macOS
  (unchanged — the slice is entirely in `crates/app`).
- **Xvfb smoke run in `archlinux:latest`** (`--console`) against a seeded
  installed Epic row whose executable is a 5-second script:
  - `Down`/`Return` on the home hero started it; the log read `stepping aside
    while gizmo-1 runs`;
  - while it ran the window was **unmapped** — `xdotool search --onlyvisible
    --name PitaGames` returned `0` windows and the root screenshot was the empty
    X background (`mean=0`);
  - when it ended the log read `Gizmo ended; asking for focus`, the window was
    mapped again (`--onlyvisible` returned `1`, screenshot `mean=3410`), and
    SQLite held the session (`epic · gizmo-1 · Gizmo · native · exit 0 ·
    duration 5 · succeeded · exited 0 after 5s`) with `playtime_secs = 5`;
  - the script is `target-arch/handoff-smoke.sh`.

## Known limits

- **The fallback badge is unit-tested but not smoke-tested.** In Xvfb the focus
  request succeeds within the grace period, so the badge never showed; forcing a
  compositor to refuse focus is not something the container can do. The
  `focus_timeout` path, the badge text and the Guide-dismiss are covered by the
  model tests only.
- **The hand-off only covers supervised, non-Steam games.** Steam starts its own
  games, so the launcher never sees a start or an exit to hand off around; a
  Steam launch in the console shell leaves the launcher on screen. Closing that
  gap needs Steam-side session detection, which is not in v1.
- **A windowed game will still show the launcher behind it.** The hand-off
  unmaps the launcher, so the desktop shows through; a fullscreen game covers
  everything as before.
- **The desktop shell does not hide.** `started(.., console=false)` returns
  `None`, so a desktop user keeps their window (and their focus) while a game
  runs. Only the console shell steps aside.
- **`reveal_window()` runs on every finished game**, even in the desktop shell
  and for a launch that never started, so a game exit always maps and focuses the
  launcher. That is the desired end state, but it means a desktop user's other
  window loses focus when a game ends.
- **The focus grace is a fixed 2 s** (`FOCUS_GRACE`), not `hide_cursor_ms` or a
  config value; a slow compositor could badge a window that would have focused.
- **Input is paused for the whole life of the game**, so the pad cannot bring the
  launcher back mid-game (the plan's badge is for *after* the game exits). A
  "press Guide to peek at the launcher" would need a new action semantic.
- **Not driven against a real store game, a real compositor, or a TV.** The
  exit path is exercised by `platform::launch`'s own tests and the smoke run's
  script; the focus behaviour is X11-without-a-WM only.
