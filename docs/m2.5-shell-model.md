# The app shell session model (M2.5)

`crates/app/src/main.rs`'s `App()` had grown into the churn epicentre of the
repo: 1,741 lines in one component, 35 signals, 12 drain futures, and every
screen receiving an explicit props struct of **signals the root owned**
(`HomeViewProps` 16 fields, `DetailProps` 13, …). Navigation, the per-screen
action channels, the hand-off, the overlay and the shared start helpers all lived
inside it, and `start_play`/`start_install` were `pub(crate)` in the root, so a
screen depended *upward* on `main.rs`.

This slice deepens that shell into a framework-free session model behind one
Dioxus seam, following the pattern the crate already uses for `play`, `handoff`,
`overlay`, `home`, `grid` and `store_installs`. See **ADR-0027** for the decision
and the alternatives.

## The seam

| Module | What it is |
| --- | --- |
| `navigation.rs` | `View` (moved out of `main.rs`) and `Navigation`: the current view, the Back target, the selected game, the library query and the text-focus flag. Framework-free, with plain methods and its own tests. |
| `session.rs` | `Session`: the shell's state behind one handle. It owns the `Navigation` and `Deref`s to it, so a screen writes `session.read().view()` and never names the inner model. |
| `context.rs` | The Dioxus seam: `provide_session(view)` (called once from `App`, using `use_context_provider`/`provide_context`) and `use_session()`. |
| `launch_start.rs` | `start_play` / `start_install` / `start_download` / `pump_installs` — the shared "start something" paths lifted out of the root. They are Dioxus-bound (they take `Signal`s), so they live here rather than in a framework-free module. |
| `pumps.rs` | The drain futures `App` runs for the window's lifetime: `activation_requests`, `downloads_actions`, `install_events`, `play_events`, plus the helpers only they use (`begin_handoff`/`end_handoff`, `handle_downloads_action`, `record_store_install`). `App` now *registers* its pumps instead of implementing the loops inline. |

A screen no longer receives `view`/`back`/`selected_game`/`query`/`text_focused`
as separate props. It calls `use_session()` and reads or writes the one handle;
`App` calls `provide_session` once and every screen below shares it.

## The consolidated idioms

Two repeated idioms became named methods on `Navigation`, so the call sites
cannot drift:

- the navigation row's `selected_game.set(None); view.set(view)` → `go(view)`
  (eight rows);
- `back.set(from); selected_game.set(Some(id)); view.set(View::Detail)` →
  `open_detail(id, from)` (the grid card, the home hero and tiles, both Osk
  paths, the detail page's Confirm, and the overlay's "Details" row).

`toggle_shell` keeps its two branches, now reading and writing the session:
entering the console shell lands on `View::Home`; leaving it returns to the
Library only when it was on the Home.

## Verification

- `cargo build -p pitagames` — clean, no warnings.
- `cargo test -p pitagames` — **209 passed** (was 204; `navigation` 4 +
  `session` 1 are new).
- `cargo clippy -p pitagames --all-targets` — clean.
- `cargo fmt --check` — clean.
- An Xvfb smoke run in the `archlinux:latest` container (`WEBKIT_DISABLE_DMABUF_RENDERER=1`,
  driven by `xdotool`, captured with `import`):
  - the window renders the grid and the header, with the nav row's active
    highlight following the session;
  - clicking **Logs** and **Stores** switches the view through `go(view)`;
  - typing in the search field drives `set_query`/`set_text_focused`;
  - `M` opens and `Escape` closes the console overlay (which exercises
    `open_overlay`, `apply_overlay`, `apply_overlay_choice`, `current_game_id`);
  - `F11` switches to the **CONSOLE** shell and lands on **Home**, and `F11`
    again returns to **DESKTOP** on the Library — both branches of
    `toggle_shell`.
  - no panic in the run's log.

## Known limits

- **The whole `Session` is one signal**, so a `use_future` that reads
  `session.read().view()` re-runs on *any* session change (the query, the
  text-focus flag) rather than only a view change. Functionally correct — the
  drain re-subscribes its channel — but a screen that re-runs its drain on every
  keystroke is a cost worth watching if a screen's drain is expensive.
- `pumps.rs` lifted four of `App`'s drains (activation, the Downloads actions,
  the install reports, the play reports). The remaining ones — the gamepad pump,
  the window key handler, the startup bootstrap — are still inline in `App` and
  are the next extraction.
- `text_focused` and `notice` are still held as their own signals where they were
  already local to a screen; only the cross-screen navigation state moved. The
  `notice` line and the shared concern handles (`Play`, `Installs`, `Downloads`)
  join the `Session` in a later slice.
- The model is tested **headlessly in the Arch container** (`crates/app` is
  bin-only and off the macOS build list), the same as every other app model.
- The overlay, the hand-off and safe mode stay separate models the session
  consults; they are not folded into the seam (ADR-0007, ADR-0022).
