# M2.5 — the two shells (`crates/core/src/ui.rs` + `crates/app/src/shell.rs`)

Status: implemented and container-verified by tests; `crates/app` builds, lints
and tests in `archlinux:latest`. The shells have not been run on the target
machines or a TV, and the console layout is still the desktop layout with a
safe-area margin and scaled chrome (see the known limits). The desktop shell is
frameless with a draggable header, and the configured monitor is applied when
the window is created.

This is the fifth M2.5 slice, on top of `crates/input` (`docs/m2.5-input.md`),
the focus graph (`docs/m2.5-focus.md`) and the gamepad pump
(`docs/m2.5-gamepad.md`). Those slices made one controller/keyboard navigation
model work on every screen; this slice makes the *window* the plan's dual shell:
a windowed desktop shell and a 10-foot console shell that share every component.

## Why this slice exists

The plan (§7 Shell) puts two shells over one component set:

- `Shell::Desktop` — windowed, decorated, 1280×800.
- `Shell::Console` — fullscreen, undecorated, with a TV overscan margin and
  larger type.

Entering console mode is `--console`, the persisted start mode, `F11`, or the
controller's `Guide` button; leaving it is the same two controls. The input
layer already emits an `Action::Guide` for the pad's `Mode` button, so the shell
switch is the first thing that action does.

## What ships

### `crates/core/src/ui.rs` — the values, no Dioxus

- `Shell { Desktop, Console }` — the runtime shell. `as_str`/`label`/
  `is_console`/`toggled`, and `FromStr` for `config.toml` and the command line.
- `StartMode { Desktop, Console, Remember }` — the persisted preference.
  `Remember` is the default and replays `last_shell`, so a fresh install opens
  the desktop shell and a returning player opens where they left off.
- `DisplayConfig` — `console_fullscreen`, `monitor`, `ui_scale`,
  `safe_area_pct`, `hide_cursor_ms`, `reduce_animations`. Every field has a
  default, so a hand-written file may name only what it changes.
- `UiConfig { start_mode, last_shell, display }`, `AppConfig { ui }` — the
  `[ui]` section of `config.toml`.
  - `UiConfig::resolve_start(requested)` — a command-line shell wins, then the
    start mode, then `last_shell`.
  - `UiConfig::remember(shell)` — records the shell the player chose; the start
    mode itself is left alone, so "always console" stays explicit.
  - `AppConfig::load(path)` — a missing file is the defaults with no warning; a
    malformed file is a warning and the defaults. A typo must never stop the
    launcher from starting.
  - `AppConfig::sanitized()` — clamps `ui_scale`, `safe_area_pct` and
    `hide_cursor_ms` into range, repairs a non-finite scale, and treats a blank
    monitor name as "primary", warning per change.
  - `AppConfig::save(path)` — atomic `.toml.tmp` + rename, like `input.toml`.

`paths::config_file()` is `<XDG_CONFIG_HOME>/pitagames/config.toml`.
`config.toml` is separate from `input.toml` because the input maps are keyed by
device GUID and owned by the framework-free input crate.

### `crates/app/src/shell.rs` — the Dioxus/tao seam

- `parse_args` — `--console`, `--desktop`, `-V`/`--version`, and an `unknown`
  list `main` warns about.
- `ShellStart` — the context `main` passes to the app: the resolved shell, the
  display numbers and the config path.
- `WindowConfig` / `window_config(shell, display)` — pure data: title,
  fullscreen, decorations, maximized, monitor, geometry. The console frame is
  undecorated; it is fullscreen by default and a maximized window when
  `console_fullscreen = false`.
- `window_builder(config)` — the startup tao builder.
- `apply_to_window(config)` — reconfigures the live window (`set_fullscreen`,
  `set_decorations`, `set_maximized`). tao's `Window` is reached through
  `DesktopService::window` because `DesktopService` has its own
  `set_fullscreen(bool)` that would otherwise win.
- `ShellState` — the live state: the `Signal<Shell>`, the display numbers
  behind an `Rc`, and the config path. `toggle()` reconfigures the window,
  flips the signal and writes the preference; a failed write is a warning.
- `base_font_px` / `root_style` / `header_style` — the CSS. The console shell
  carries a `safe_area_pct` padding and a larger base type; both shells set
  `--ui-scale`, which the nav and the header title read. Both branches name the
  same properties on purpose: Dioxus's style setter re-adds a property a new
  style string omits, so a console-only `padding` would survive the switch back.

### `crates/app/src/main.rs`

`main` parses the arguments, loads the config (warnings to stderr), resolves the
shell, and builds the window for it *before* launching, then passes `ShellStart`
as a Dioxus context.

`App` holds `ShellState` and:

- intercepts `Action::Guide` in the window key pump and the gamepad drain — the
  shell's own action, handled before the screen sees it — so `F11` and the pad's
  `Mode` button toggle from anywhere;
- renders the root with `root_style`, the header with `header_style`, a shell
  badge and, in console mode, the "Guide or F11 returns to the desktop" hint.

`crates/input` gained `Key::F11`, bound to `Action::Guide` in the keyboard
layout, so a remap will cover it like every other binding.

## The frameless desktop shell and the startup monitor

The desktop shell matches the plan's frameless description and the monitor
preference is honoured when the window opens, not only on a toggle.

- **The pure display model** (`pitagames_core::ui`): `MonitorInfo { name, x, y,
  width, height }` (physical pixels) with `center(width, height)` — the top-left
  a window needs to sit centred on the monitor, pinned to the origin when the
  window is larger than the screen. `select_monitor(name, monitors)` returns the
  index of the attached monitor a configured name selects, or `None` for the
  primary (no name, or a name that is not attached). `placement(name, width,
  height, monitors)` folds the two into a `Placement::{Default, Center { x, y
  }}`. `DisplayConfig::select_monitor`/`placement` delegate to them.
- **The window seam** (`crates/app/src/shell.rs`): `WindowConfig::desktop()` is
  now `decorations: false`. `WindowConfig::startup_placement(&monitors)` is the
  pure seam; `place_at_startup(&Window, &WindowConfig)` is the tao adapter.
- **Why `with_on_window`**: a monitor handle only exists once the window is
  built, so the name cannot be resolved in `window_builder`. `main` passes
  `Config::with_on_window`, which Dioxus calls after `Window::build` and before
  the webview is created: a windowed shell is centred on the configured monitor
  with `set_outer_position`, and a fullscreen console shell is put on it with
  `Fullscreen::Borderless(Some(handle))`. With no configured monitor the window
  is left on the primary, which is the platform default.
- **The drag header**: the desktop header carries `onmousedown` →
  `Window::drag_window()` (tao's `begin_move_drag`); the search field and the
  window controls `stop_propagation` so a press on them never starts a drag. The
  header also carries **Minimize** and **Close** buttons
  (`shell::window_control_style`, which names the hit floor), because a
  frameless window with no way to close would trap the player. The console shell
  keeps its own window and draws none of this.
- **The plan's `app-region: drag` is not used**: WebKitGTK does not implement the
  `-webkit-app-region` property, and this Dioxus build ignores a `<style>`
  element anyway (see `docs/m2.5-design.md`), so the drag is a tao call from the
  event handler instead.

## Verification

- `pitagames-core`: **96** tests (`ui` adds 12: defaults, start-mode
  precedence, `remember`, a missing/broken/partial file, clamping, NaN repair, a
  blank monitor, a save/load round trip, wire names, the CSS helpers).
- `pitagames-input`: **56** tests, including the keyboard layout's `F11` →
  `Guide` binding.
- `crates/app`: **145** tests (`shell` adds 9: argument parsing, the version
  flag, unknown flags, both window configs, the windowed console, the root
  styles naming the same properties, the UI-scale multiplication and the
  scaled header title).
- `cargo clippy --all-targets -- -D warnings` and `cargo fmt --all -- --check`
  are clean on macOS for the pure crates and in `archlinux:latest` for
  `crates/app`.

No Xvfb smoke run covers the shells yet: the switch is pure window flags plus
CSS, and the container has no window manager to exercise fullscreen. A desktop
run with `--console` and `F11` is the next smoke run.

## Known limits

- **The console layout is still the desktop layout.** This slice ships the
  window, the switch and the display numbers; the 10-foot type pass over the
  cards and the shelves/Continue-hero home are later slices. The chrome (nav,
  header) scales, the per-screen type does not.
- **The desktop shell is frameless with an in-app titlebar.** The header drags
  the window and carries minimize/close; there is no resize grip, so a
  frameless window is resized by the window manager's own shortcut (or a later
  slice adds edge grips). The drag uses tao's `begin_move_drag`, which is
  reliable on X11 and best-effort on Wayland (a compositor may refuse a move
  without a pointer serial).
- **The monitor preference now applies at startup**, but a name that is not
  attached silently falls back to the primary. The centring assumes a scale
  factor of 1 (see the 4K note below).
- **4K/HiDPI is explicitly deferred.** The startup placement compares the
  logical window size against the monitor's physical geometry and ignores the
  scale factor, and the container has no window manager or scale factor to
  exercise a HiDPI path. A real 4K display on the RX 9070 is the check; until
  then nothing here claims a 4K-correct placement.
- **The cursor auto-hide uses a fixed 2 s.** Last-input tracking now ships
  (`docs/m2.5-hints.md`) and hides the pointer when the pad is active, but it
  reads a hard-coded 2 s rather than the parsed `hide_cursor_ms`, which is still
  only clamped and carried.
- **No TV and no hardware.** Safe area, 10-foot readability and fullscreen are
  unvalidated on the RX 9070 / RX 5700 XT and marked "not tested on a TV".
