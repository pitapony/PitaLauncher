# M2.5 — the gamepad pump (`crates/app/src/gamepad.rs`)

Status: the pump and its wiring are implemented; `crates/app` builds, lints and
tests in `archlinux:latest` (the `gilrs` worker can only build there). The pump
now lives in `App` and posts each action into the active screen's
`ActionChannel`; the Library, Downloads, Stores and detail screens each drain
their own channel and own their own `ScreenFocus`. Nothing here has been
exercised against a real controller on the target machines — a headless
container has no evdev node, so only the pure `Pump` rules and the action
channel are covered by tests.

This is the third M2.5 slice, on top of `crates/input` (`docs/m2.5-input.md`)
and the focus graph (`docs/m2.5-focus.md`). The input layer answers *what action
did the player press*; the focus graph answers *which cell does that action move
to*; this slice answers *what produces the action when there is a controller
instead of a keyboard* — the console shell's input loop.

## Why this slice exists

`crates/input` shipped with a `GilrsSource` and a `ReplaySource`, and the focus
graph shipped with a **keyboard** pump in `LibraryGrid` — but nothing in the GUI
opened `gilrs`, so a real controller could not move the ring. The plan's
immediate next step is exactly that gap (`plan §14.5`): wire the one
`GilrsSource` → `Input` → the *same* focus graph the keyboard already drives.
The whole point of the shared `Action` table is that the two devices converge on
one navigation model, so the pad must not grow its own button handling; it must
emit the same actions the keyboard does and call the same code.

Hardware-independent apart from the device itself — the pump's rules are tested
through `ReplaySource` — so it ships while the M0 hardware closer waits on
machine access.

## What ships

### `Pump` — the pure loop body

```text
source.poll() ─┐
               ├─► Input::handle(event, now) ─┐
source.poll() ─┘      …                        ├─► Vec<ActionEvent>
               Input::tick(now) ──────────────┘
```

- `Pump::new(maps)` owns one [`pitagames_input::Input`] and nothing else.
- `Pump::seed(source)` connects the devices a source already reports. This
  matters because `gilrs` does not necessarily emit a `Connected` event for a
  pad that was already plugged in when the backend opened; without the seed a
  pad present at startup would be silent until it was replugged.
- `Pump::step(source, now)` drains **every** waiting raw event into one tick and
  then fires the repeats now due. One call is one frame; the injected `Instant`
  keeps the deadzone, the dominant-axis resolver and the 400 ms/80 ms repeat
  testable without a device and without a `sleep`.

### `GamepadChannel` and `spawn` — the window seam

- `GamepadChannel` is the same shape as `play::PlayChannel` and
  `store_installs::InstallChannel`: one drain future owns the receiver behind a
  `Rc<AsyncMutex<Option<_>>>`, because a `use_hook` value must be `Clone` and an
  `UnboundedReceiver` is not one.
- `spawn(maps, sender)` runs `Pump` on a `pitagames-gamepad` thread over a real
  `GilrsSource`, polling every `POLL_INTERVAL` (16 ms ≈ 60 Hz). A backend that
  cannot be opened, or a thread that cannot be started, is reported as
  `GamepadEvent::Unavailable(message)` — a log line, never a crash. The thread
  exits the moment `unbounded_send` fails, which is what happens when the grid
  unmounts and the receiver is dropped.
- `GamepadEvent` carries either an `Action(ActionEvent)` (press, release or
  repeat) or the `Unavailable` message.

### One action path per screen

The pump lives in `App` and does not call a screen's navigation code directly.
It posts the `Action` into the active screen's `ActionChannel`; the screen owns
its own `ScreenFocus` and drains its channel in a future. `dispatch_action`
chooses the channel by `view()`:

- **Library** → `LibraryGrid`'s channel, whose `perform_action` moves the ring,
  scrolls the focused row into view and opens the focused card.
- **Downloads** → the inline `handle_downloads_action` in `App`, whose cells are
  the store-install rows (Clear finished / Cancel / Retry / Remove).
- **Stores** → `StoresView`'s channel, whose cells are the three top actions and
  one per store row, or the sign-in modal's Cancel/Close and Send buttons.
- **Detail** → `Detail`'s channel, whose cells are Back and Play.
- **History / Account / Logs** → no graph yet; `Back` returns to the Library.

The keyboard pump and the gamepad drain both call `dispatch_action`, so a pad
and a keyboard converge on the same action and the same screen. A `Released` is
ignored — the graph is positional, not a hold — and only a direction ever
repeats. The `ActionChannel` is a `futures_channel` mpsc whose receiver sits
behind an `AsyncMutex`, so the channel is `Clone` and one screen owns the
consumer at a time. The action body is a free function per screen rather than a
shared closure because the callers are a window event handler and an async
future, which cannot capture one closure without wrapping it in an `Rc`.

### Lifecycle

The pump is hosted by `App`, so one `gilrs` source serves the whole window. Each
screen's drain future starts when the screen mounts and stops when it unmounts;
the channel keeps queued actions until the screen drains them. The Library's
channel is the only one whose scroll geometry lives in the grid; the other
screens keep their geometry in their own components. The pump thread exits when
the app's receiver drops, so closing the window stops the pad.

## Verification

`crates/app` builds (with `gilrs` linking `libudev`/`systemd-libs`), lints with
`clippy --all-targets -- -D warnings`, is `cargo fmt --all -- --check` clean, and
passes **136** tests in `archlinux:latest`. The pump adds 7 unit tests over
`ReplaySource` with an explicit clock; the action channel adds 3 more:

- a seeded pad turns a d-pad button into `NavigateDown` with no `Connected`
  event;
- a `Connected` event alone also registers a pad, and both events in one step
  report one press;
- a held direction repeats at 399 ms/400 ms and on the 80 ms interval;
- a diagonal stick push (X dominant) is one `NavigateRight`, not two actions;
- a push inside the radial deadzone produces nothing;
- a press and release in one tick are reported in order (press before release);
- an unbound button produces nothing;
- a tao key the keyboard layout binds becomes the shared `Key`, and an unbound
  key stays with the webview;
- an action channel delivers actions in order;
- a cloned channel shares the one receiver.

No test opens a device: the real `GilrsSource` is only constructed inside the
worker thread, which a unit test never starts.

An Xvfb smoke run in `archlinux:latest` with a fixture Steam root of 8 games and
**no controller** proved the worker does not take the app down and that the
keyboard path is unchanged by the `perform_action` refactor:

- the window came up and the library rendered, with the `pitagames-gamepad`
  thread running (a machine with no evdev node does not abort startup);
- `Down` entered at the first card with the ring, `Right` moved to the next
  column with exactly one ring, and `Return` opened that card's detail page.
  Screenshots `target-arch/smoke-gp-focus-{1,2,3}.png`.

The multi-screen slice is compile/lint/test verified but has **not** had its own
Xvfb smoke run yet; the Stores, Downloads and Detail rings share the Library's
`ring_style`, and a controller-driven walk of those screens is the next smoke
run. The pad half cannot be exercised here either: the container has no
`/dev/input`, so the `GilrsSource` event path (button/axis conversion, the
L1/L2 swap, battery) is covered only by its own `crates/input` tests.

## Known limits

- **No graphs on History, Account or Logs.** The Library, Downloads, Stores and
  detail screens each have a `ScreenFocus` and a drain; the three remaining
  screens still navigate by pointer. `Back` leaves them for the Library.
- **No remap UI.** `input.toml` is still hand-edited; the in-app remapping
  screen is a later slice. The glyph hints and the cursor auto-hide now ship
  (`docs/m2.5-hints.md`), but the hint row reads the *built-in* gamepad layout
  rather than the last pad's GUID remap, because the pump does not hand the
  GUID up to `App`.
- **No actionable permission message.** A backend that cannot open is logged;
  the "add your user to the `input` group" copy the plan calls for is not shown
  in the UI yet.
- **Not driven against a real controller** on the RX 9070 / RX 5700 XT. The
  container has no evdev node, so the `GilrsSource` path (button/axis/power
  conversion, the L1/L2 swap) is covered only by its own `crates/input` tests,
  not end to end.
