# M2.5 — the focus graph

Status: the pure graph, the desktop shell's keyboard navigation and the gamepad
pump that drives the same graph are implemented and verified on macOS (the
`pitagames-input` tests) and in `archlinux:latest` (the `crates/app` tests plus an
Xvfb smoke run). Nothing here has been exercised against a real controller on the
target machines. The Library, Downloads, Stores and detail screens each have a
graph; History, Account and Logs still navigate by pointer.

This is the second M2.5 slice, on top of `crates/input` (`docs/m2.5-input.md`).
The input layer answers "what action did the player press"; this slice answers
"which cell does that action move to", which is what lets a controller walk a
grid without a pointer.

## Why this slice exists

M2.5 turns the launcher into a controller-only 10-foot shell. That needs three
things, in order:

1. one action table (`crates/input`, shipped);
2. a spatial graph that turns a direction into the next cell (this slice);
3. the shell actually pumping device events and moving the ring (the keyboard
   pump is here; the gamepad pump that drives the *same* graph is
   `docs/m2.5-gamepad.md`).

The graph is deliberately its own module, framework-free, because the plan's
renderer boundary forbids DOM focus and JavaScript navigation, and because a
graph that can be fed `(rows, columns, direction)` is trivially unit-testable —
which a webview is not.

## What ships

### `crates/input/src/focus.rs` — the graph, no Dioxus

- `FocusId(u64)` — a screen-chosen stable identity. The library grid uses the
  cell's index in the filtered list, so the focused id doubles as the list
  position to draw and scroll to.
- `FocusNode { id, row, col }` — one cell in the screen's logical layout. Rows
  run top to bottom, columns left to right; a shelf, a grid and a dialog's button
  row are the same shape to the resolver.
- `FocusGraph` — the cells plus the one that is focused. Cells are always kept
  sorted by `(row, col, id)`, so iteration and tie-breaks never depend on
  registration order.
  - `insert(id, row, col)` registers a cell (idempotent; re-registering moves an
    id's coordinates and re-sorts).
  - `grid(item_count, columns)` builds a row-major rectangular grid whose ids
    are the indices — the one constructor the library grid uses. A zero column
    count is treated as one column so a screen measured before its first resize
    still behaves.
  - `focus(id)` / `focus_index(Option<usize>)` set the focused cell; an unknown
    id, `None`, or an index past the end is refused/clears focus.
  - `focused()`, `focused_node()`, `focused_index()` read it back.
  - `resolve(action)` answers the next cell **without moving** focus, for a
    screen that wants to peek.
  - `move_focus(action)` applies it: the first navigation on an unfocused screen
    enters at the first cell (so a pad/keyboard can enter without a pointer), a
    non-navigation action leaves focus alone, and an empty graph returns `None`.

**The resolver.** For one direction, every cell strictly in that half-plane is
ranked by a single `SortKey`
`(diagonal, primary * 2 + perpendicular, perpendicular, primary, row, col, id)`
(lower wins). A straight candidate (`perpendicular == 0`) always beats a
diagonal one; among equals the primary distance dominates and the perpendicular
distance is the tie-break; anything still tied falls through to `(row, col, id)`.
That last term is what makes the answer deterministic and independent of
insertion order.

**Per-axis wrap, no traps.** When nothing is strictly in the direction, `wrap`
flips only the moved axis to its far end and keeps the other axis fixed:

- right from a row's rightmost cell lands on that row's leftmost cell;
- down from the bottom row lands on the top of the same column;

and the mirror for left/up. A one-cell row or column has nowhere to go and
returns `None` — that is a dead end, never a trap, because the other axis still
moves. A test walks a BFS from every cell of several grids (including a ragged
last row) and asserts every cell reaches every other.

### `crates/input` support

- `Action::is_navigation()` — the four `Navigate*` actions, in one place, so the
  pump and the graph agree about what moves focus.
- `InputMap::action_for_key(Key)` — the action the keyboard layout binds a key
  to. The GUI translates a window key event into the **same action a pad would
  emit**, so remapping `Enter`/`Space` in `input.toml` moves the graph without
  the GUI hard-coding bindings. A hand-edited duplicate is deterministic
  (`Action::ALL` order wins). `F` is bound to `Search` (the on-screen keyboard
  slice); the app's pump yields every key to a focused text field, so `f` still
  types an `f` there.

### `crates/app/src/focus.rs` — the thin Dioxus seam

- `ScreenFocus` / `use_focus()` — one screen's focused cell in a signal, so a
  move re-renders only the screen that owns it. It starts **unfocused**: the ring
  appears on the first navigation, not when a pointer merely happens to be over
  the window.
- `ScreenFocus::move_focus(action, count, columns)` rebuilds the pure graph from
  the screen's *logical* list on every move (`FocusGraph::grid` +
  `focus_index`), applies the action, and stores the new index. The graph is not
  stored: virtualization draws only a window of rows, but focus must still walk
  past the drawn edge and scroll it into view. A focused index the list no longer
  contains falls back to the first cell, exactly like the first navigation.
- `ring_style(focused)` — the focus ring. It recolours the card's existing 1 px
  border and adds a `box-shadow`, neither of which changes layout, so a ring can
  never shift the grid under the pointer.
- `key_from_tao(KeyCode)` — translates a tao physical key into the shared closed
  key set. Only keys the keyboard layout binds are translated; everything else is
  `None`, so typing, shortcuts and text entry the launcher does not own keep
  working.

### `crates/app/src/grid.rs` — scroll-into-view arithmetic

- `GridGeometry::row_of(index)` — the row a linear item index occupies.
- `scroll_into_view(scroll_top, viewport_height, geometry, row, margin)` — the
  smallest scroll that brings a row into the viewport, with a margin so the
  focused card is not flush against the edge. The row pitch includes the gap
  below the row, so the card's real bottom is `top + row_height - ROW_GAP`.
  Without a measured viewport or row height it returns the offset unchanged; a
  negative offset is clamped to the top.

### `crates/app/src/main.rs` — the key pump and the action channel

The **window-level key pump** lives in `App`
(`dioxus::desktop::use_wry_event_handler`), so one pump serves every screen. DOM
focus is deliberately not part of navigation: the events are read from tao
rather than a focused element, so the same code path the gamepad pump uses
drives them.

The pump:

1. ignores key releases and OS repeats of non-navigation actions (a held arrow
   repeats movement, `Confirm`/`Back` stay one press);
2. yields to a text field while it is focused (`onfocus`/`onblur` track it),
   because arrows there move a caret, not the screen;
3. maps the key through `pitagames_input::InputMap::keyboard()`
   (`action_for_key`) to an `Action`;
4. calls `dispatch_action`, which posts the action into the active screen's
   `ActionChannel` by `view()`.

The Library's channel drains into `perform_action`, which:

- for navigation, resolves the new cell, computes the scroll target, updates the
  window model and scrolls the mounted container imperatively
  (`MountedData::scroll(PixelsVector2D, ScrollBehavior::Instant)`);
- for `Confirm`, opens the detail page for the focused card — the same route a
  card click uses.

The Downloads screen's channel drains into `handle_downloads_action`; the Stores
screen's into `StoresView`; the detail screen's into `Detail`. Every card draws
`ring_style(focused)` and a click sets the focus to that card, so mouse and
controller converge on one focus.

## The stale-ring finding

`outline` and `border-color`/`box-shadow` both failed at first: every card the
focus passed through kept its ring. The cause is in Dioxus's style setter, not
WebKit: `dioxus-interpreter-js` snapshots an element's existing inline styles,
sets the new `style` attribute, then **re-adds any property the new string
omits** ("Preserve the styles that were not updated"). An unfocused ring that
emitted the empty string therefore never cleared the properties it had set.

The fix is that the unfocused value names the same properties with neutral
values (`crates/app/src/focus.rs`), so the property is always present in the new
string and is updated rather than preserved. The smoke run then showed exactly
one ring per move.

## Verification

- `pitagames-input`: **56** tests (up from 39; 16 in `focus`), clippy
  `-D warnings` and `rustfmt` clean on macOS and in `archlinux:latest`.
- `crates/app`: builds, clippy `-D warnings`, `fmt --check` and **136** tests
  (the 4 `grid` tests, the 7 gamepad tests and the 3 action-channel tests
  included) in `archlinux:latest`.
- Xvfb smoke run in `archlinux:latest` against a fixture Steam root of **60**
  games (5 columns), keyboard-only:
  - no ring on load (`focus-0-initial`);
  - the first `Down` enters at the first cell (`focus-1-entry`);
  - `Right` walks the row and wraps from the last column back to the first
    (`focus-2-wrap`);
  - `Down` past the viewport scrolls the focused row into view with its margin
    (`focus-3-scrolled`);
  - `Return` opens the detail page of the focused card (`focus-5-detail`);
  - exactly one ring is drawn at every step after the style fix.
  Screenshots `target/smoke/focus-*.png`.

## Known limits

- **The gamepad drives every screen's graph** (`docs/m2.5-gamepad.md`): the pump
  lives in `App` and posts each action into the active screen's `ActionChannel`.
  The Library, Downloads, Stores and detail screens each drain their own channel
  and own their own `ScreenFocus`. History, Account and Logs still navigate by
  pointer; `Back` leaves them for the Library. The pad has not met a real
  controller.
- **No remap UI.** `input.toml` is hand-edited; the in-app remapping screen is
  still planned.
- **The graph is rebuilt per move** (`FocusGraph::grid` over the filtered list).
  That is cheap for a windowed grid and keeps the list authoritative; a very
  large library could instead cache the graph and invalidate on a list change.
- Focus is **not** set by a pointer hover, only by a click or a navigation. A
  later slice decides whether the mouse should move the ring.
- The scroll offset is not restored when leaving and returning to the Library
  view (the component remounts at the top, unchanged from
  `docs/m1-virtualized-grid.md`).
- Not run against a real controller or a live Steam library on the RX 9070 /
  RX 5700 XT yet.
- **The on-screen keyboard is the graph's newest consumer**
  (`docs/m2.5-osk.md`): its ragged key grid is a `FocusGraph` whose ids are the
  flat key indices, and the sheet is opened by `Action::Search` (the keyboard's
  `F`, the pad's `North`) and walked with the same navigation actions. With the
  sheet open the screen hands every action to
  `OnScreenKeyboard::handle` before its own graph, so a direction moves the key
  ring instead of the cards and `Back` cancels the edit.
