# v1.1 — the console session (`crates/core/src/session.rs` + the session files)

Status: implemented; `pitagames-core` builds, lints and tests on macOS and in
`archlinux:latest` (**157** tests, 13 of them `session`), and `crates/app` builds
and lints in `archlinux:latest`. **Nothing here has been driven on a TV or a
login screen** — no TV is attached to either in-house machine (ADR-0004), so the
whole session ships marked **"not tested on a TV"**.

This is ticket #44 of the v1.1 console session. It adds the session-file
generator, the systemd user unit, the `--session` plumbing and the overlay's
exit-to-desktop row. `platform::power` (the logind half, ticket #43) already
ships; the TV checklist and the EAC-entry interaction are ticket #45.

## Why this slice exists

The plan's v1.1 exit criteria:

> "PitaGames (console)" at the login screen boots fullscreen, launches a game
> inside the same gamescope instance, and returns to the launcher on exit with no
> nested gamescope and no focus loss.

In-app console mode already ships (`F11`/`Guide`, the console shell, the overlay).
The login-screen session is the missing piece: a display-manager entry, a
compositor that owns the output, and a launcher kept alive inside it.

## What ships

### The generated session files (`crates/core/src/session.rs`)

Two files, generated from [`DisplayConfig`], never hardcoded:

* **the wayland-sessions entry** (`packaging/pitagames-session.desktop`, installed
  to `/usr/share/wayland-sessions/pitagames.desktop`; a checkout writes
  `$XDG_DATA_HOME/wayland-sessions/pitagames.desktop`). Its `Exec` is
  `gamescope … -- systemctl --user start --wait pitagames-session.service`.
* **the systemd user unit** (`packaging/pitagames-session.service`, installed to
  `/usr/lib/systemd/user/pitagames-session.service`; a checkout writes
  `$XDG_CONFIG_HOME/systemd/user/pitagames-session.service`). `ExecStart=pitagames
  --console --session`, `Environment=PITAGAMES_SESSION=1`, `Restart=on-failure`,
  `After=graphical-session.target`.

The gamescope arguments come from `[ui.display.session]` in `config.toml`
(`SessionDisplay` on `DisplayConfig`):

| config | gamescope |
| --- | --- |
| `session.resolution = { width, height, refresh_hz }` | `-w <width> -h <height> [-r <refresh>]` |
| `[ui.display] monitor = "HDMI-A-1"` | `--prefer-output HDMI-A-1` |
| `session.hdr = true` | `--hdr-enabled` |
| `session.vrr = true` | `--adaptive-sync` |

With no `session.resolution` **nothing is pinned** — gamescope runs the output's
preferred mode — so the shipped session is never a hardcoded resolution. A zero
width/height drops the whole resolution with a warning, a zero refresh drops just
the rate.

The rendering is a contract, exactly like the desktop entry:
`packaging/pitagames-session.desktop` and `packaging/pitagames-session.service`
are the default rendering byte for byte, and a `pitagames-core` test asserts it.
`pitagames-cli session --print` / `--print-unit` regenerate them:

```text
pitagames-cli session --print      > packaging/pitagames-session.desktop
pitagames-cli session --print-unit > packaging/pitagames-session.service
```

`pitagames-cli session` with no action prints the status of both files (current /
stale / absent); `--write` and `--remove` do what they say; `--path` /
`--unit-path` aim them elsewhere; `--exec` overrides the unit's launcher argv.

### No nested gamescope

The entry starts **one** gamescope around the launcher's unit; the launcher never
starts a second compositor. `PITAGAMES_SESSION=1` is the signal the launch path
already reads to suppress a per-game gamescope wrapper
(`platform::envc::wrapper_steps` / `platform::launch::runtime_wrappers`). `--session`
sets that variable in the launcher process (and the unit sets it in the
environment), so a game renders inside the session's gamescope, never inside a
nested one.

### The GUI writes them (a checkout) — `crates/app/src/session_entry.rs`

On startup, and exactly like the generated `.desktop` entry, the launcher writes
the two files into its own XDG directories **unless** a packaged copy exists in
the XDG data directories / systemd user unit directories, or
`PITAGAMES_NO_SESSION_ENTRY` is set. The unit's `ExecStart` points at the running
binary, so a rebuilt or moved checkout still starts. Every failure is a warning,
never a reason to keep the window from opening.

The package installs the same files to `/usr/share/wayland-sessions` and
`/usr/lib/systemd/user` (see `packaging/PKGBUILD`).

### Never the default session

Nothing selects the session as the display manager's default. It is one login
option among the others; the user picks it, and the DM remembers the last choice,
so **exit-to-desktop ends the session and the next login returns to it**.

### Exit to desktop (`crates/app/src/overlay.rs`)

The overlay grows a fourth power row in the session, **Exit to desktop**
(`overlay.exit_to_desktop`), carrying
`OverlayChoice::Power(PowerAction::TerminateSession)`: it asks logind to terminate
the caller's session (`loginctl terminate-session`), which ends gamescope and the
unit. Off the session there is nothing to exit, so the row is absent. The action
itself is #43's; this slice only adds the row.

## The TV checklist and the EAC entry

The session ships **"not tested on a TV"** (ADR-0004). The human gate is the
checklist at the end of [`docs/console-mode.md`](console-mode.md#tv-checklist-not-yet-run):
the in-app console walk plus the session's **resolution switching, HDR,
VRR/adaptive-sync, overscan/safe-area and focus return**, and the EAC-entry block.
A `pitagames-core` docs-agreement test reads that document and asserts the
checklist keeps covering those topics and keeps the marker, so an edit cannot
silently drop an acceptance line. The full beta walk is
[`docs/beta-testing.md`](beta-testing.md).

The two unverified seams to look at first on a TV:

* `journalctl --user -u pitagames-session` — the unit's own log;
  `Restart=on-failure` hides an early crash otherwise.
* whether gamescope's **`WAYLAND_DISPLAY`** reached the unit. The entry starts
  the unit with `systemctl --user` *inside* gamescope, so the socket should be
  inherited — confirm with `systemctl --user show-environment` if the launcher
  cannot open a Wayland connection.
* `systemctl --user daemon-reload` if the unit was written this boot and the
  display manager did not list it.

### The EAC entry

The session boots into a **normal** entry by default, so an **EAC Linux v2** game
started from the couch still needs the CachyOS **EAC entry**. The game page
surfaces the same "reboot into the EAC entry and play" guidance as the desktop
shell, and `PITAGAMES_SESSION=1` keeps suppressing a per-game gamescope wrapper
there too. See [`docs/eac-v2.md`](eac-v2.md) and ADR-0031. What matters here:

* **PitaGames's own processes are user-space** — the launcher, WebKitGTK/GTK,
  Mesa and gamescope — so the launcher and the session run on the EAC entry;
  nothing in the session needs a kernel module.
* **DKMS modules do not load in the EAC entry.** The EAC kernel loads only
  modules signed when it was built, so NVIDIA, ZFS and r8125 come from
  `linux-cachyos-eac-*` packages and other DKMS modules (for example
  `virtualbox-host-dkms`) will not load. Kernel-level overlays and mods do not
  work either; the user-space overlays — gamescope itself and MangoHud — still
  do. The validated in-house paths are AMD/Mesa and need no DKMS module.
* Injection stays **hard-off** for a protected game, even on the entry.

## Verification

- `pitagames-core` gained **12** `session` tests: the default session pins no
  resolution; the entry wraps the unit and not a nested launcher; a configured
  resolution / HDR / VRR / monitor drive their flags; the entry renders a
  wayland-session; the unit runs `--console --session` with `Restart=on-failure`;
  a launcher path with spaces is quoted; an empty launcher is refused; the
  packaged files match the renderer; and install/remove round-trips. `DisplayConfig`
  gained **3** `[ui.display.session]` tests (default, round-trip, a bad mode is
  dropped with a warning) and `paths` one for the two new file locations.
- `crates/app`'s `overlay` gained **1** test (the session's exit-to-desktop row is
  enabled and absent off the session; the session now carries `PowerAction::ALL`),
  and `shell` one for the `--session` flag forcing the console shell.
- `pitagames-cli` gained **2** tests (the `session` argument parser; write → read
  back → remove against temp paths).
- A `session` docs-agreement test reads `docs/console-mode.md` and asserts the TV
  checklist still covers resolution, HDR, VRR, overscan, focus return, the
  console session and the EAC entry, and keeps the `"not tested on a TV"` marker
  (#45), so a docs edit cannot silently drop an acceptance line.
- `cargo clippy --all-targets -- -D warnings` and `cargo fmt --all -- --check` are
  clean for the pure crates; `crates/app` is linted and tested in
  `archlinux:latest`.

## Known limits

- **Never run on a TV or a login screen.** No TV is attached in-house, so the
  session file, the compositor flags and the login flow are tests and docs only
  (ADR-0004). Ticket #45's checklist is the human gate.
- **The wayland-environment hand-off is unverified.** The entry starts the unit
  through `systemctl --user`, so the unit must see gamescope's `WAYLAND_DISPLAY`.
  On a `systemd --user` session that is a normal environment inheritance, but it
  is exactly the kind of compositor/library detail no container can check; it is
  a first thing to look at on a TV (`journalctl --user -u pitagames-session`).
- **No confirmation dialog** on exit-to-desktop, mirroring the other power rows
  (#43's limit). The DM's remembered session is what makes "next login returns to
  it" true; a DM that resets to its own default would need a per-DM preference we
  do not write.
- **`systemd --user` may need a reload** after the unit is first written; newer
  systemd watches `~/.config/systemd/user` and reloads by itself, older versions
  need `systemctl --user daemon-reload`.
