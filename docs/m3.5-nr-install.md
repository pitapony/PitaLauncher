# M3.5 — the in-app NR installer and model sourcing

`platform::nr` decides whether neural rendering is offered and which pinned
release backs it; this slice is the step after that. It runs upstream's
unmodified `install.sh` **in-app** on the shared terminal, answers nothing on the
user's behalf, captures the launch options it prints, and sources the one file
that is not in the package — the NR model.

Ticket: #29 (part of umbrella #8).

## Pieces

| Crate | Responsibility |
|---|---|
| `stores::mod_install` (`pitagames-stores`) | the installer relay on the shared PTY driver: stream, prompt policy, the `%command%` capture, transcript, cancel |
| `platform::nr_install` (`pitagames-platform`) | the pre-flight form, the model scan, the PE version check, and the `install.sh` argv |
| `app::nr_install` (`pitagames`) | the adapter that drives `stores::mod_install` on the shared terminal |
| `app::nr_install_view` (`pitagames`) | the Graphics screen's pre-flight panel and terminal sheet |

```text

      │                              │
      │                              ▼
      │                    app::nr_install ──► app::terminal ──► stores::mod_install ──► PTY
      │                              │                                   │
      └── scan()/inspect_model() ──► FoundModel              captured: mods::capture
```

## The pre-flight form

`InstallForm` carries the plan's choices: **route** (fixed to `optiscaler` — the
field exists so the screen draws it and `plan` refuses anything else), **network**
(`NrModel`), **processing** (`NrProcessing`), **model scale**, and **model
source** (`ModelSource`). `InstallForm::validate` refuses a non-OptiScaler route;
the ReShade feeders are post-v1 and are never installed.

## The model

The weights are NVIDIA's and are in no package. They are read from the user's own
`nvngx_dlssnr.dll` (or a zip carrying it), whose version comes from its **PE
version resource** (`nvngx_dlssnr.dll` → `FileVersion`, via `goblin`), and only
`310.9.16` (preferred) and `310.8.0` are accepted. A fourth component
(`310.9.16.0`) is tolerated.

- `scan(roots)` walks the game's install directory and, for a non-Steam game, its
  Wine prefix's `drive_c` (bounded by depth and entry count), verifying every
  `nvngx_dlssnr.dll` it finds. `ModelScan::offers_picker()` is the cue to offer
  the file picker.
- `inspect_model(path)` is the picker's check: read the version, refuse an
  unsupported one by name.
- **The launcher never copies the model.** It passes the *original path* on
  `--dll`, and `plan` refuses a source inside the launcher's own XDG trees
  (`is_launcher_owned`). The package caches the extracted weights in **its own**
  directory (`<package>/dlssnr-amd`), and the UI states `DO_NOT_SHARE` plainly.

## Running the installer

`plan(form, package_dir, exe)` produces an argv-only command — never a shell
string — whose working directory is the **game executable's directory**:

```text
bash <package>/install.sh <exe dir> --dll <model path> --model <name>
```

A `CachedInPackage` source passes no `--dll`. A missing `install.sh`, a missing
model, or a model in a launcher tree is refused before anything runs.

`stores::mod_install::InstallRun` then runs it on the same PTY driver the store
CLIs use (`stores::cli`), so it gets the two-lock poll, the idle/hard timeouts,
the process-group cancel and the per-run transcript for free.

## The prompt policy: never guessed

Only an **acknowledgment** is answered: a line mentioning `press enter` / `press
return` / `press any key` is answered with a newline and reported as
`InstallStep::Continued`. A line ending in `:` or `?` is a **question** and is
surfaced as `InstallStep::Prompt` for a typed answer. The installer's own route,
network, processing and model prompts are upstream's; the launcher never picks
one for the user.

## Capture

Every line the installer prints is accumulated and handed to `mods::capture`, so
a printed `WINEDLLOVERRIDES="dxgi=n,b" %command%` line becomes a `CapturedEnv`
with no copy-and-paste. The adapter exposes it through a shared slot the screen
reads when the run succeeds; wiring it into the profile's `captured_env` and the
profile file is ticket #30 (the ini surface and forced env).

## Verification

Pure crates (macOS host and CI):

```bash
cargo test -p pitagames-platform nr_install
cargo test -p pitagames-stores mod_install
cargo clippy -p pitagames-platform -p pitagames-stores --all-targets
cargo fmt --all -- --check
```

`mod_install` covers: a fixture `install.sh` running to completion through the
PTY with its transcript captured; an unknown prompt surfaced and its typed answer
passed through; an ENTER courtesy auto-answered; the installer running in the
given working directory; a cancel reporting `cancelled`; and the line classifier.
The transcript test also asserts a printed `%command%` line is captured.

`nr_install` covers: the PE version resource of a synthetic `nvngx_dlssnr.dll`
read and accepted, a fourth component tolerated, an unsupported version refused
by name, a non-PE file rejected; the scan finding a fixture DLL with preferred
versions first, a prefix scan under `drive_c`, an unsupported DLL listed but not
accepted, and the picker offered on an empty scan; the composed argv with the exe
directory as cwd and the package cache directory beside the script; a cached
model needing no `--dll`; a missing installer/model refused; the route fixed to
OptiScaler; and a model inside the launcher's trees refused.

The GUI is built and linted in `archlinux:latest` (`CARGO_TARGET_DIR=/work/target-arch`).

## Known limitations

- **Not run against a real release.** The package is fetched by ticket #12, whose
  live HTTP `Fetcher` is still its open item; the panel can only run an installer
  that is already on disk (the container smoke run seeds a fixture `install.sh`).
- **The package directory defaults to `<data>/pitagames/mods/dlssnr/<backend>/<version>`**
  and is editable in the panel; the model cache lives inside it, so it is the
  package's own directory rather than a central model store.
- **The picker is a path field, not a native file dialog** — this Dioxus/WebKit
  build has no file-dialog binding wired.
- **The panel's controls are pointer/tab reachable but are not on the screen's
  gamepad focus graph yet**; wiring them into `graphics::Control` is a follow-up.
- **A Steam game's Wine prefix is not scanned** (the panel uses
  `platform::prefix::dir`, which covers the non-Steam per-game prefixes); a Steam
  game is covered by its install directory.
- **`--model` names are our mapping onto upstream's flag**; if upstream renames
  one, the installer's own prompt is still surfaced, so this is a non-fatal
  mismatch.
- Not validated on the RX 9070 or the RX 5700 XT.
