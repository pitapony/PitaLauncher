# M2.5 — the console home (`crates/app/src/home.rs` + `crates/app/src/home_view.rs`)

Status: implemented; `crates/app` builds, lints and tests in `archlinux:latest`
(**169** tests, up from 152) and an Xvfb smoke run in the same container
rendered the shelves and walked them with the keyboard. Nothing here has met a
real controller or a TV.

This is the eighth M2.5 slice, on top of the input layer
(`docs/m2.5-input.md`), the focus graph (`docs/m2.5-focus.md`), the gamepad pump
(`docs/m2.5-gamepad.md`), the shells (`docs/m2.5-shells.md`), the hints
(`docs/m2.5-hints.md`) and the remap UI (`docs/m2.5-remap.md`). Those made one
controller/keyboard navigation model work on every screen; this slice is the
screen the console shell actually opens on: the couch **Home**.

## Why this slice exists

The plan's console home (plan §7, *Console mode*) is "a full-bleed **Continue**
hero (last played, art, Play/Install), then shelves: Recently played, Installed,
one row per store. Horizontally scrolled, virtualized tiles." The console shell
already opened on it in the previous slices' wiring — `View::Home` existed and
`--console` started there — but the home was a placeholder: it had no shelves, no
hero and no focus graph. This slice builds the screen.

It is hardware-independent (the same fixture Steam root the other smoke runs
used), so it ships while the M0 hardware closer waits on machine access.

## What ships

### `crates/app/src/home.rs` — the layout, framework-free and unit-tested

The module owns the *shape* of the screen, so the renderer stays thin and the
arithmetic is testable without a webview, exactly like `crate::grid`.

- **`ShelfKind`** (`RecentlyPlayed`, `Installed`, `Store(Store)`) and **`Shelf
  { title, kind, games }`** — one row, its heading and the indices into
  `Library::games` it draws.
- **`Home::build(&Library)`**:
  - the **hero** is the most recently played installed game, then the most
    played, then the first installed game, then the first game at all, so the
    couch always has something to press Play on;
  - the shelves are **Recently played** (installed games with a `last_played`,
    newest first, capped at `RECENT_LIMIT`), **Installed**, then **one per
    store** in product order (Steam, Epic, Amazon, GOG, Local); empty rows are
    dropped rather than drawn as a heading with nothing under it.
- **`HomeCell`** (`Hero` or `Tile { shelf, item }`) and the flat `cells` list in
  layout order. A cell's id **is its index in that list**, which is what lets a
  `ScreenFocus` store it like a grid index.
- **`Home::graph()`** builds the **ragged** `FocusGraph`: the hero on row 0, one
  row per shelf. The resolver's diagonal fallback and per-axis wrap keep a short
  shelf reachable from a long one with no trap.
- **`cell`/`id_of`/`game`/`tile_of`** map between a focus id, a cell and the
  library index it draws.

### The horizontal window (virtualization)

A shelf can hold a thousand owned games, so `shelf_window(item_count,
tile_width, gap, scroll_left, viewport_width, overscan)` returns the tiles to
draw and where to place them — the mirror of `crate::grid::window` for one row
that scrolls sideways. `shelf_scroll_into_view` is the mirror of
`crate::grid::scroll_into_view`: it moves as little as possible, so walking a
shelf does not jiggle the row, and a margin keeps the focus ring off the edge.

### `crates/app/src/home_view.rs` — the Dioxus seam

- The **Continue hero** is a full-bleed card: hero art (header image, else
  background), the `Continue` label, the title, the meta line and a Play /
  Install / Details row whose primary button is chosen by `primary_action`
  (`Play` when the row can play and is wired, `Install` when it can install,
  else open Details).
- Each **shelf** is a heading plus a horizontally-scrolled container. Only
  `shelf_window`'s tiles mount; a full-width sizer keeps the scrollbar honest.
  A pointer wheel/touchpad scroll is recorded in `shelf_scroll` so the windowed
  tiles follow.
- **Focus drives both scroll axes.** A navigation action resolves the next cell
  through `Home::graph()`, updates the focused shelf's horizontal window and
  slides it, then pulls the whole shelf row into the vertical view
  (`scroll_to_with_options(Nearest)`). `Confirm` runs the hero's primary action
  and opens the detail page for a shelf tile; `Back` leaves the screen.
- Clicking a card sets the focus to that card's **global** id and opens Detail,
  so mouse and controller converge on one focus.

### `crate::start_play` / `crate::start_install` — one launch path

The hero's Play/Install buttons need the same behaviour the grid's card buttons
and the detail page's Play button had inline. Those two functions moved to
`main.rs` as `pub(crate)`:

- `start_play(game, playtime, play, play_events, notice, db)` — a Steam row asks
  Steam to launch itself (and records the playtime Steam will not); every other
  store starts the supervised hand-off.
- `start_install(id, title, installs, install_events, events, board, libraries,
  notice, view)` — a Steam row installs through `steam://install` and the board
  follows the manifest; a CLI store runs its own client on the serial queue.

The grid and the detail page now call them too, so the three surfaces cannot
drift.

### Back returns to the screen the page was opened from

A game can be opened from the grid **and** from the console home, so the detail
page's Back cannot be hardcoded to the library. `App` now owns
`detail_back: Signal<View>`; the screen that opens a page records itself there
first, and the detail page's Back button (and its `Esc`) returns to it. The
button's label follows (`← Home` / `← Library`).

### A GTK Escape de-dupe

GTK/WebKit delivers one `Escape` as **two** identical `KeyboardInput` presses
(it reaches both the window and the webview), so the app's window key pump
ignores a raw key that repeats back-to-back with no other event within 50 ms.
Without the guard a single Back press popped two screens (`Detail → Home →
Library`). Arrows are not duplicated, and a held key repeats far more slowly
than the window, so normal auto-repeat is untouched.

## Verification

- `crates/app`: **169** tests (up from 152), of which **15 `home` + 1
  `home_view` + 1 `detail`** are new: hero selection, the fallback chain, the
  shelf order, the cells over ragged rows, `id_of`/`cell` round-tripping, the
  graph rows, the shelf window at the top / scrolled / past the end / empty, the
  scroll-into-view margins, and `primary_action` per install/launch state.
- `cargo clippy -p pitagames --all-targets -- -D warnings` and `cargo fmt --all
  -- --check` are clean in `archlinux:latest`; the pure crates pass on macOS.
- Xvfb smoke run in `archlinux:latest` against the fixture Steam root:
  - the console shell opens on the home with the **Continue** hero and the
    `INSTALLED` / `STEAM` shelves, each tile showing its capsule art;
  - `Down` from the hero enters the first shelf, `Right` walks the row and the
    shelf scrolls; the focus ring lights **exactly one** tile (an early build
    compared a shelf-local index, so every shelf's tile of the same position lit
    up — `Home::id_of` fixed it);
  - the hero's Details button and a shelf tile both open the detail page, and
    **Back returns to the home** (both the button and `Esc`);
  - the hero's Play button asks Steam to launch the app (the container has no
    Steam, so the expected `Could not ask Steam to run appid …` notice shows).

## Known limits

- **`Back` on the home leaves to the Library**, matching the plan's "Back leaves
  each screen". The console home is the shell's root, so a Back that stayed put
  would be defensible too; it is left as-is because the nav bar (Home / Library
  / …) is shown in both shells.
- **The tiles do not scale with `--ui-scale`** (`SHELF_TILE_WIDTH` is fixed), so
  the scroll arithmetic and the CSS agree; scaling the tiles is part of the
  later 10-foot design pass.
- **The hero is a fixed height** (`44vh`, min 260 px), not measured, so a very
  large UI scale could clip its content.
- **The Escape de-dupe is a 50 ms window on the raw key.** It fixes the double
  Back press; if a future GTK/WebKit deliver a *different* duplicate (e.g. a
  key with a modifier), the same idea applies.
- **Not driven against a real controller or a TV.** The pad half is covered only
  by the pump's `ReplaySource` tests, and no TV is attached to either machine.
