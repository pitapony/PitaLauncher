# M2.5 — the test backbone: property tests, replay fixtures and layout snapshots

Status: implemented. Every new test is a **pure-crate** test, so it runs on
macOS and in `archlinux:latest` with no webview and no Xvfb. The layout
snapshots are the guaranteed headless path; RSX snapshots through `dioxus-ssr`
are not viable in this build (see *The `dioxus-ssr` spike*), and the Xvfb smoke
runs stay the visual gate.

This is the test slice that closes M2.5's testing gap, on top of the focus graph
(`docs/m2.5-focus.md`), the console library (`docs/m2.5-console-library.md`) and
the home shelves (`docs/m2.5-home.md`). It adds no product behaviour: it makes
the layouts those slices draw **provable** and their regressions catchable
without a TV.

## Why this slice exists

M2.5 shipped a controller-first shell whose navigation is a pure graph, but the
only proof the graph could not trap the ring was one hand-written BFS over a few
rectangular grids. Three things were missing:

- the **ragged** layouts (the console library's chip row over its tiles, the
  home's Continue hero over variable-length shelves) had no reachability proof;
- the controller path had no **recorded fixtures** — the `ReplaySource` existed
  but nothing fed it a transcript and asserted the actions;
- a **layout regression at a resolution** (1080p vs 4K) had no cheap gate short
  of an Xvfb run.

## What ships

### The shared layout model — `crates/input`

The tests have to exercise the *real* layouts, and `crates/app` cannot build on
macOS (Dioxus/WebKit), so the two pure layout pieces the screens draw from moved
into `pitagames-input` and the app now consumes them:

- **`FocusGraph::ragged(&[Band])`** (`crates/input/src/focus.rs`) — the one
  ragged-layout builder. A [`Band`] is a run of cells that starts on a fresh row
  and wraps every `columns`; ids are the flat cell indices across all bands. The
  console library's chip-over-tiles graph is
  `ragged(&[Band::new(chips, chip_columns), Band::new(tiles, tile_columns)])` and
  the home is `ragged(&[hero, ..one band per shelf])`, so both screens walk one
  graph implementation and the property tests cannot drift from what the app
  renders.
- **`crates/input/src/layout.rs`** — the responsive numbers the grid shares:
  `H_PADDING`, `TILE_MIN_WIDTH`, `TILE_MIN_WIDTH_CONSOLE`, `COLUMN_GAP` and
  `fit_columns(available, min_width, gap)`. `crates/app/src/grid.rs` re-exports
  the constants and calls `fit_columns` from `GridGeometry::with_floor`, so the
  1080p/4K column counts the snapshots pin are the ones the grid renders.

### Property tests — every layout is trap-free

`crates/input/src/focus.rs` gains one helper, `assert_trap_free(graph)`, which
proves two properties through the graph's public moves:

- **reachability** — from every cell, a sequence of the four directions reaches
  every other cell, so no layout can strand the ring;
- **determinism** — the answer from a cell is identical when the same cells are
  registered in reverse, so two identically built screens cannot diverge.

It is applied to the three shapes the shell draws:

- `every_cell_of_a_rectangular_grid_reaches_every_other` — the windowed grid,
  over square, wide, single-column and single-cell grids;
- `every_cell_of_a_ragged_chip_over_tiles_graph_reaches_every_other` — the
  console library, sweeping 0/1/5/8 chips, 1/3/5 chip columns, 0/1/6/13 tiles and
  1/2/5/11 tile columns (a wrapped chip row, a partial last tile row, and a
  no-chip row);
- `every_cell_of_the_home_shelves_reaches_every_other` — the home, over a
  one-tile shelf beside a long one and shelves shorter than the hero's column.

### Replay fixtures — recorded transcripts to actions

`fixtures/input/` holds three JSON transcripts and
`crates/input/tests/replay_fixtures.rs` replays each through the shipped
`ReplaySource` into an `Input`, asserting the exact `Action`/`ActionKind`
sequence (and that a press/release transcript produces no repeat events):

- `pad-menu-walk.json` — the d-pad, `South` (Confirm), `Start` (Menu), `East`
  (Back), `Mode` (Guide) and the right bumper (TabNext);
- `keyboard-walk.json` — the arrows/WASD, `Enter`, `Escape`, `F` (Search), `M`
  (Menu), `F11` (Guide), `Tab` and `Q`;
- `stick-deadzone.json` — a stick push inside the radial deadzone (silent), then
  a diagonal that clears it (one direction) and a vertical dominance switch
  (release before press).

A fixture is a transcript, not a device: the test drives the same `ReplaySource`
the app's pump uses, so a recorded session and a unit test are one code path.

### Layout snapshots at 1080p and 4K

`crates/input/tests/layout_snapshots.rs` renders the pure layout model to a
stable text form and snapshots it with `insta`:

- `console-library-1080p` / `console-library-4k` — the console grid's chip row
  over a 12-tile grid, at the width-dependent tile columns;
- `grid-columns` — the console and desktop column counts at both resolutions;
- `home-shelves` — the hero over four shelves of lengths 3/1/5/2.

Each snapshot test also asserts the worked resolution→columns example (console 5
at 1080p, 11 at 4K; desktop 7 and 16), so a blind `cargo insta accept` cannot
quietly accept a layout regression. The snapshots are committed under
`crates/input/tests/snapshots/`; regenerate with `INSTA_UPDATE=always cargo test
-p pitagames-input` or `cargo insta review`.

## The `dioxus-ssr` spike and the fallback

The plan wanted RSX snapshots at 1280×800, 1920×1080 and 3840×2160. We did not
get a working `dioxus-ssr` render, and the blocker is structural, not a missing
feature flag: the app's screens are not pure render functions. They read live
`Signal`s, translate tao key codes (`dioxus::desktop::tao::keyboard`), mount
webview handles (`onmounted` / `MountedData::scroll`) and install a window-level
key pump (`use_wry_event_handler`). `dioxus-ssr` renders a component tree with
none of those desktop APIs, so rendering a screen under it would first require
splitting every screen into a pure render plus a desktop adapter — a worthwhile
refactor, but a product change, not a test slice.

The **guaranteed path** is therefore the pure-model `insta` snapshot above: it
covers the layout *numbers* (columns, the ragged cell positions) the screens are
built from, runs on macOS and in the container, and needs no webview. The
**visual gate** stays the Xvfb smoke runs (`target-arch/*.sh`), which exercise
the real RSX at 1080p.

## Verification

- `pitagames-input`: **123** tests (116 unit + 4 snapshot + 3 replay), clippy
  `-D warnings` and `rustfmt` clean on macOS and in `archlinux:latest`. New:
  `Band`/`FocusGraph::ragged` (4), `layout::fit_columns` (3), the two new
  property tests, the `assert_trap_free` helper, the 3 replay fixtures and the 4
  snapshots.
- `crates/app`: builds, clippy `-D warnings`, `fmt --check` and the app tests
  pass in `archlinux:latest`; the `grid`/`filter`/`home` tests that assert the
  column counts, the ragged cell positions and the hero-over-shelves graph are
  unchanged and still pass against the shared builder.
- No new dependency in the app: `insta` and `serde_json` are `pitagames-input`
  dev-dependencies only.

## Known limits

- **The property tests are exhaustive sweeps, not a property-testing framework.**
  The spec's dependency list added `insta` only, so the reachability proof is the
  shipped BFS run over a curated parameter set rather than `proptest`/`quickcheck`
  over the integers. The set covers the shapes a real library reaches (empty,
  wrapped, partial, ragged) but is not a proof over every `usize`.
- **No RSX/visual snapshot in this slice.** The `dioxus-ssr` path is documented
  as not viable; the Xvfb runs are the only thing that renders the real RSX, and
  their scripts/screenshots stay untracked (`target-arch/` is gitignored), as in
  `docs/m2.5-console-library.md`.
- **The snapshots pin the pure model, not the pixels.** They catch a column or a
  cell-position regression; they do not catch a colour, a font or a scroll bug —
  that is the visual gate's job, and it has not run against a real TV (ADR-0004).
- **Not run against a real controller.** The fixtures replay recorded events
  through `ReplaySource`; `gilrs` button/axis conversion on hardware is still
  uncovered.
