# v1.1 — power over logind (`crates/platform/src/power.rs` + the overlay rows)

Status: implemented; `pitagames-platform` builds, lints and tests on macOS and in
`archlinux:latest` (**219** tests, 5 of them `power`), and the console overlay's
power rows enable in the console session (`crates/app` builds and lints in
`archlinux:latest`). Nothing here has been driven against a **real logind**, and
the action itself is polkit-gated, so the copy ships without a hardware claim
(ADR-0004).

This is ticket #43 of the v1.1 console session. It adds the host half
(`platform::power`) and wires the console overlay's previously-disabled power rows
to it. The gamescope session unit, the session-file generator and the TV checklist
are the rest of v1.1 and are separate tickets.

## Why this slice exists

The plan's console-shell table (plan §7, *Console mode*) lists **Overlay** as:

> `Guide`/`Start`: resume, graphics, store page, power (suspend/restart/shutdown),
> exit console mode, controller + battery status, clock.

The M2.5 overlay shipped the menu with the power rows **shown but disabled** —
"arrives with the console session" — because a couch user should see the row
rather than wonder where it went, but a half-implemented shell-out would be worse
than the placeholder. v1.1 owns the console session, so the rows become real: a
couch user controls the machine from the pad.

## What ships

### `crates/platform/src/power.rs` — the host half, behind a trait

- **`PowerAction::{Suspend, Restart, Shutdown, TerminateSession}`** — the four
  actions, with `ALL`, the three-action `MENU` the overlay lists, a lowercase
  `label()` and `Display`. The plan's power menu is suspend / restart / shut down;
  `TerminateSession` is `loginctl terminate-session`, the action behind
  exit-to-desktop (no menu row yet — see Known limits).
- **`PowerError::{Refused { action, message }, Unavailable { message }, Unsupported}`**
  — a refusal names the action and the reason; `Unavailable` is a bus/logind that
  could not be reached; `Unsupported` is a platform with no logind.
- **`PowerBackend`** — the one-method trait a power action crosses:
  `request(&self, action) -> Result<(), PowerError>`. Implementations must not
  block forever or spawn a process.
- **`request(action)`** — the app's entry point. On Linux it connects to the
  **system bus** and calls logind; on any other platform it reports
  `PowerError::Unsupported` (a total function, so the app has no platform branch).
- **`logind::Logind`** (`#[cfg(target_os = "linux")]`) — the only place in the
  workspace that speaks to logind. `org.freedesktop.login1` on the system bus:
  `Manager.Suspend(true)`, `Manager.Reboot(true)`, `Manager.PowerOff(true)`, and
  `Manager.TerminateSession(<this session id>)`. The session id comes from
  `Manager.GetSessionByPID(std::process::id())` then the session object's `Id`
  property — explicit rather than the `session/self` alias, which would be a
  guess.

### No shell, ever

The action is a **D-Bus method call**, not a process: no `loginctl`, no
`systemctl`, no `sh`. This is a hard rule (AGENTS.md "Launch composition is
argv-only" and the ticket's "never shelling out"): a power action that shells out
would be a second privileged path with its own argument-injection surface. Every
method is **polkit-gated**, and the call passes `interactive = true` so polkit may
prompt the user instead of refusing outright. The launcher runs no privileged
code and never touches `/proc` or the kernel directly.

### Overlay wiring (`crates/app/src/overlay.rs`, `crates/app/src/main.rs`)

- **`OverlayChoice::Power(PowerAction)`** joins `Close`/`Details`/`StorePage`/
  `ToggleShell`, and **`OverlayContext`** gains a `session` flag
  (`runtime::session_mode()` = `PITAGAMES_SESSION=1`).
- **`Overlay::build`** emits the three plan rows. In the session they are
  **enabled** and carry an `OverlayChoice::Power`; off the session they stay
  **visible but disabled** with "available in the console session". The rows never
  say "arrives with the console session" again.
- **`apply_overlay_choice`** runs `OverlayChoice::Power(action)` through
  **`spawn_power`**, which calls `power::request(action)` on the blocking pool
  (`tokio::task::spawn_blocking`) — a polkit prompt can hold the D-Bus call open
  and must not block the event loop. A refusal lands in the notice line as
  `Could not <action>: <message>`; a success says nothing, because the machine is
  already suspending or powering off.

## Verification

- `pitagames-platform` gained **5** `power` tests (**219** total): every action is
  listed once, the three-action `MENU` is exactly the overlay's rows, a fake
  backend records every action, a refusal names the action and the reason, and a
  source guard proves the module never constructs a process (no shelling out). The
  fake is the trait seam; the real `Logind` impl is `cfg(target_os = "linux")` and
  is compile-checked in `archlinux:latest`, so the crate still builds and tests on
  macOS.
- `crates/app`'s `overlay` module gained **1** test (**10** total) by splitting the
  old placeholder test in two: the power rows are **enabled in the session**
  (each finds an `OverlayChoice::Power` row, `is_enabled()`, and no "arrives"
  copy) and **disabled off the session** (each row is `!is_enabled()` and reads
  "available in the console session").
- `cargo clippy --all-targets -- -D warnings` and `cargo fmt --all -- --check`
  are clean for the pure crates; `crates/app` is linted in `archlinux:latest`.
- The Linux `zbus` backend is compile-checked in `archlinux:latest` (zbus 5 with
  its default `blocking-api` feature). No live logind is exercised anywhere.

## Known limits

- **Never run against a real logind.** The container has no logind and no polkit,
  so the D-Bus path is compile-checked only; the model and the overlay rows are
  what the tests drive. A real suspend/restart/shutdown is a hardware/host action
  and stays a human gate.
- **The session-enabled smoke run is visual only.** Pressing a power row in the
  container would ask the host's logind to act; the smoke run therefore checks
  that the rows render enabled under `PITAGAMES_SESSION=1` and disabled without
  it, and never presses one.
- **No confirmation dialog.** The polkit prompt (when a policy needs one) is the
  confirmation; the overlay row itself fires immediately. A couch user who wants a
  second tap before shutdown is not served yet.
- **`TerminateSession` has no overlay row yet.** It is modelled and the CLI/API
  can call it, but exit-to-desktop is the session unit's job and lands with it.
