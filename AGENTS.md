# AGENTS.md

## Agent skills

### Issue tracker

Issues and specs live as GitHub issues in `pitapony/PitaLauncher`, driven with the
`gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

The five canonical triage roles, each label string equal to its name
(`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`).
See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `AGENTS.md` (this file) is the vocabulary source and `docs/adr/`
holds the decisions. See `docs/agents/domain.md`.

### Workflow integration

This project uses Matt Pocock's engineering workflow. When processing feature requests, bug fixes, or architectural changes, map user intent to these lifecycle skills:

- **"Brainstorm / Grill me"** → Invoke `grill-me` or `grill-with-docs` to pressure-test assumptions.
- **"Write a spec / PRD"** → Invoke `to-spec` before writing implementation code.
- **"Break this down into tasks"** → Invoke `to-tickets`.
- **"Implement / TDD"** → Invoke `tdd` (red-green-refactor at pre-agreed seams), then `implement`.
- **"Handoff / Clean up session"** → Invoke `handoff` to compress context into a clean markdown document.

*Rule:* Never jump straight to raw code generation for complex tasks if a lifecycle skill matches the request. Always load and follow the corresponding skill via OpenCode's native skill mechanism.

## Build & verify

- **Local (macOS host)** — build/test only the pure-Rust crates:
  `cargo test -p pitagames-core -p pitagames-db -p pitagames-art -p pitagames-metadata -p pitagames-platform -p pitagames-stores -p pitagames-secrets -p pitagames-input -p pitagames-shim -p pitagames-cli`
  plus `cargo clippy --all-targets` and `cargo fmt --all` over the same list. Do not build `crates/app` locally.
- **MSRV is 1.89** (edition 2024 + let-chains; `keyring` 4 needs 1.88, the single-instance `std::fs::File::try_lock` needs 1.89). Clippy's `collapsible_if` only suggests let-chains at that MSRV, which is why the pure crates use them; keep `rust-version` in `Cargo.toml` at 1.89 or higher.
- **The single-instance lock is `flock`-based** (`core::lock::InstanceLock`, `$XDG_DATA_HOME/pitagames/pitagames.lock`): the GUI takes it before creating its window; when it is busy, the second launch asks the running instance to come to the front through the activation socket and exits `0`. The shim and the CLI deliberately do not take the lock, so they still run alongside the GUI. It is advisory and released by the kernel on exit/crash. Details in `docs/m1-single-instance.md` and `docs/m1-desktop-integration.md`.
- **Safe mode is a supervisor + child split** (`crates/app/src/safe_mode.rs` + `crates/app/src/supervisor.rs`, `docs/m2.5-safe-mode.md`, ADR-0007): `main` is the **supervisor** (takes the lock, spawns `current_exe()` with `PITAGAMES_GUI_CHILD=1`); the **child** builds the webview and writes the ready file from `App`'s first render. `--safe-mode`, `[ui] safe_mode` in `config.toml`, and `PITAGAMES_SAFE_MODE=1` (the supervisor's retry) all OR together; safe mode sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` before WebKit starts and forces `reduce_animations`, which emits one global `<style>` (no animation/transition/`backdrop-filter`; a `Safe mode` chip in the header). A child that crashes **before** its first render is retried once in safe mode; a crash **after** it is restarted, capped at `MAX_RESTARTS = 3`. `PITAGAMES_FAKE_WEBVIEW_FAILURE=1` is the documented test hook the smoke run uses (it only fires when safe mode is off). The lock lives in the supervisor, the activation socket in the child.
- **Desktop integration is generated, not installed:** `core::desktop` renders `packaging/pitagames.desktop` byte-for-byte (a `pitagames-core` test asserts it). On startup the GUI writes `$XDG_DATA_HOME/applications/pitagames.desktop` pointing at the running binary, unless a packaged entry exists in `XDG_DATA_DIRS` or `PITAGAMES_NO_DESKTOP_ENTRY` is set; `pitagames-cli desktop-entry [--print|--write|--remove] [--exec <path>] [--path <file>] [--json]` is the diagnostic (`--print > packaging/pitagames.desktop` regenerates the checked-in copy). Single-instance focus is a Unix socket (`core::activation`, `<data>/pitagames/instance.sock`, one line `focus` → `ok`, `0600`, stale files probed and removed): the GUI binds it after the lock and raises the window from the event loop, `pitagames-cli activate [--socket <path>] [--json]` is the client. The tray icon (`crates/app/src/tray.rs`) is built manually because Dioxus's `init_tray_icon` panics; without a StatusNotifier host the launcher runs without one, and because `libappindicator` panics inside `dlopen` when its library is missing, the build runs under `catch_unwind` with the panic hook muted. The window/tray icon is painted in `crates/app/src/icon.rs` (twinned with `packaging/pitagames.svg`). Close still quits: no close-to-tray. Details in `docs/m1-desktop-integration.md`.
- **Packaging lives in `packaging/`:** `PKGBUILD` (named `pitagames-git` until there is a release tag; `provides`/`conflicts=('pitagames')` already match the release name) installs `/usr/bin/pitagames`, `/usr/bin/pitagames-cli`, the shim as `/usr/lib/pitagames/pitagames-shim` with a `/usr/bin/pitagames-shim` symlink (Steam launch options contain that name), `pitagames.desktop`, the hicolor SVG `Icon=pitagames` resolves to, the AppStream metainfo (`io.github.pitapony.PitaGames`, launchable `pitagames.desktop`) and `compat/*.toml` to `/usr/share/pitagames/compat`. `depends` is what the binary actually links — `webkit2gtk-4.1`, `gtk3`, `openssl`, `xdotool` (for `libxdo`) — plus `libayatana-appindicator` (dlopen'd by the tray, invisible to `ldd`/`namcap`) and `xdg-utils`; `umu-launcher`, Proton builds, gamescope/MangoHud/gamemode and the store CLIs stay optdepends. `makepkg` refuses to run as root, so verify as a non-root user (`fakeroot`, `debugedit`, `git`; `makepkg -e` reuses the source/target tree), then `pacman -U`, `appstreamcli validate --no-net`, `desktop-file-validate` and `namcap`. No `.SRCINFO` is checked in for a `-git` package (it changes every commit); it is generated at AUR submission. Details in `docs/m1-packaging.md`.
- **The M2 store CLIs share one driver** (`stores::cli`, `docs/m2-cli-backend.md`): a `CliSpec` holds the program plus one argv template per command (`{id}`/`{dir}`/`{parent}`/`{name}` substituted verbatim, one pass, never a shell string), `CliHandle::spawn` runs it on a PTY (child is a session leader with the PTY as its controlling terminal), a reader thread tees raw bytes to `cli-<program>-<command>-<nanos>-<pid>.log` and streams parsed `ProgressEvent`s, and `next_event`/`write_stdin`/`cancel`/`wait`/`drain` drive it (`drain(&self)` is `wait` without giving up the handle, for the interactive flows). The handle carries **two locks** — the state and the reader's channel — because the poll waits on the channel outside the state lock: with one lock, a thread that only ever arrived between two polls was starved (a `cancel()` took ~12 s in the container), and an interactive flow needs a second thread to answer a prompt while this one blocks. Timeouts are per run — idle 5 min + hard 6 h for installs, hard 10 min only for `CliOptions::interactive()` auth — and a timeout or `cancel()` sends `SIGHUP`, then `SIGKILL` to the process group after a 2 s grace. The tests use `#!/bin/sh` fake CLIs injected through `CliOptions::env["PATH"]` (POSIX built-ins only, verified in the Arch container, where `/bin/sh` is bash in POSIX mode); the two timeout tests synchronise through a marker file the fake CLI writes, not through sleeps, so they do not race startup. A PTY echoes typed input, so an auth run's log/tail can contain the pasted auth URL/code — local diagnostics only, never into SQLite or the UI. `CliCommand` covers list/auth/logout/sync/install/verify/launch/status/version; `install` templates interpolate `{id}`/`{dir}`/`{parent}`/`{name}`, and `verify`/`launch` may use `{dir}` too (an optional install dir — `gogdl` needs `--path` for both), while a `{dir}` a command cannot supply is a `CliError::Template`, never a dropped argument. A command whose `CliSpec` template is empty is `CliError::Unsupported` (never an argument-less run), and `StoreStatus` (`probe`d from `PATH`, `Ready`/`CliMissing`) lives here so every backend shares it. The driver starts the child in `$HOME` unless `CliOptions::cwd` is set, so a relative `--program` does not resolve; use absolute paths.
- **Run verdicts are shared too** (`stores::report`, `docs/m2-cli-backend.md`): some wrapped CLIs log an error and exit `0`, only the line layout differs, so `LogFormat::{Legendary,Nile,Gogdl}` (`[cli] INFO: …` vs `INFO [CLI]:\t …`; `Gogdl` is `gogdl`'s `[NAME] INFO:` and parses like `Legendary`), `LogLine { level, source, message }`, `RunReport` (`succeeded()` = exit 0 + no `ERROR`/`CRITICAL`/`FATAL` line, `exited_cleanly()` = exit 0 only, `log_lines()` for per-store markers), `RunFailure`/`require_success()` and the PTY-tolerant `extract_json` live there. `stores::epic` re-exports its types, so the split did not move any caller.
- **The first backend on that driver is Epic** (`stores::epic`, `docs/m2-epic.md`; `pitagames-cli epic …`): the `legendary` argv presets (`list --json`, `list-installed --json`, `status --offline --json`, `--version`, `auth --disable-webview`, `auth --delete`, `install {id} --base-path {parent} --game-folder {name} --yes --disable-sdl`, `verify {id}`, `launch --skip-version-check {id}`), the JSON parsers that tolerate a PTY-merged `[cli] INFO:` stream, DLC filtering (`metadata.mainGameItem`/`is_dlc`), the code-paste auth relay, and `install_dir()` = `<XDG_DATA_HOME>/pitagames/games/epic/<sanitized name>` (`core::paths::games_dir()` + `core::paths::safe_component`). **Two legendary exit-0 traps**: `verify` exits `0` for corrupt/missing files, so the verdict is parsed from the summary line (`VerifyReport`), and some refusals log an error and still exit `0`, so `RunReport::succeeded()` also requires no error line while `launch` uses `exited_cleanly()` because the game shares the PTY. The auth flow gets its verdict from `Epic::report(&CliCommand::Auth, outcome)`, because a refusal after the prompt also exits `0`. `PROGRESS_PATTERN` matches only legendary's download/verify lines, not the install summary's compression percentage. Fixtures in `fixtures/legendary/` are the shapes from legendary's source — **not yet driven against a real `legendary`**, which no target machine has.
- **The importers are read-only and installed-only** (`stores::import`, `docs/m2-importers.md`; `pitagames-cli import [--heroic <dir>]... [--lutris <dir>]... [--bottles <dir>]... [--json]`): Heroic's config folder (`legendaryConfig/legendary/installed.json`, `gog_store/installed.json`, `nile_config/nile/installed.json`, `sideload_apps/library.json`) plus its cached `store_cache/gog_library.json` and nile's `library.json` for titles (Amazon reuses `amazon::installed_state` and `amazon::parse_owned`), Lutris' `pga.db` **SQLite** database (the plan's `~/.local/share/lutris/games/*.yml` only holds runner config — the titles, install directories and the installed flag are in the database, opened `SQLITE_OPEN_READ_ONLY` with a create-less read-write fallback, queried `SELECT *` and read by column name so schema drift costs one field), and Bottles' `library.yml` (a `serde_norway` YAML map of uuid to entry, read for `id`/`name`/`source`/`store` — its bottle path stays unread because a Windows program path needs the prefix). Imported games keep the identity their store uses (a Heroic Epic `app_name` is the same `GameId` `legendary` reports) and are tagged `imported:<launcher>`, so `import::merge(library, imported)` adds only what is missing. Heroic's roots, Lutris' data dir and Bottles' base are `$XDG_CONFIG_HOME`/`$XDG_DATA_HOME` plus the three Flatpak `~/.var/app/<id>/…` copies; the CLI flags replace one launcher's roots at a time, so a fixture tree can be scanned beside a real install. Failure is per source: a missing file is `(missing)`, an unparsable one is an error for that source alone (exit stays `0`, like `compat`), a broken title cache is a warning that costs titles and never rows, and duplicates are dropped by `GameId`. Dependencies added to `pitagames-stores`: `rusqlite` (0.32, `bundled` — the same `libsqlite3-sys` 0.30 `pitagames-db`'s `sqlx` links) and `serde_norway` (the maintained `serde_yaml` fork). Fixtures in `fixtures/heroic/` + `fixtures/bottles/library.yml` (the Lutris database is built in the test, so no binary blob is checked in) — **not yet run against a real Heroic, Lutris or Bottles install**.
- **Non-Steam prefixes, disk space and the install queue** (`platform::prefix`, `platform::disk`, `stores::queue`, `docs/m2-prefixes.md`; `pitagames-cli prefix <store> <id> [--root <dir>] [--proton <path>] [--json]`, `pitagames-cli disk <path> [--need <size>] [--json]`): Steam keeps each game's Wine prefix in `steamapps/compatdata/<appid>`, so every other store gets one directory per game at `<XDG_DATA_HOME>/pitagames/prefixes/<store>-<id>` (`$PITAGAMES_PREFIX_DIR` or `--root` moves the root; the id runs through `paths::safe_component`, so a hostile store id cannot escape the root, and the key is also the umu `GAMEID`). `prefix::is_initialized` reads `drive_c`/`system.reg`/`user.reg` so "present" and "initialized" stay distinct, `prefix::umu_env` returns the `GAMEID`/`PROTONPATH`/`WINEPREFIX` map `umu-run` takes, and `prefix::inspect` reports path/size/state — read-only, nothing is created or deleted. `disk::space` is `statvfs` (no `df`; `available`, not `free`, is what an install checks), `disk::dir_size` is a bounded symlink-free walk (200k entries / depth 32) so sizing a prefix cannot hang, and `disk::check` turns a required size into an `ok()`/`shortfall()` verdict; `disk::human_bytes` is the CLI's formatter. `stores::queue` is the serial install queue the three CLI backends share (Epic/Amazon/GOG keep session and cache state in `~/.config`, so two installs at once fight): a pure `InstallQueue` of `InstallJob`s moved through `Queued → Running → Done | Failed | Cancelled`, `enqueue` refusing a duplicate active id, `start_next` starting at most one job (`Busy` otherwise) after the disk pre-check (a size-less job or an unknown answer skips the check, a refused job is marked `Failed` and reported `Skipped`), `finish`/`progress` ignoring a late report from a cancelled backend, and `cancel`/`retry`/`remove`/`clear_finished`. - **The umu/Proton hand-off turns a store prefix into a running game** (`platform::launch`, `app::play`, `docs/m2-launch.md`; `pitagames-cli launch <store> <id>` and the grid/detail Play buttons): `prepare(&Handoff)` composes the argv-only launch from the store's `Game` row plus the *same* `profiles/<store>-<id>.json` the shim reads (`platform::envc` stays the only compiler), so `LaunchMode::Umu` is `umu-run <exe>` with `GAMEID`/`PROTONPATH`/`WINEPREFIX` from `prefix::umu_env` and `STORE` (`epic`/`gog`/`amazon`/`steam`/`none` — umu's own vocabulary), while a native executable runs directly with the profile's wrappers and no umu variables. A row is Windows when its exe ends in `.exe` or it carries the `platform:windows` tag the backends set; `prepare` refuses Steam (it launches itself), an uninstalled row, a row with no executable *and no client*, an executable that vanished (one `stat`, error names the path) and a Windows build with no Proton. **A row whose store names no executable takes a third shape**: `Handoff::client` carries a `LaunchSpec` that `stores::launch::client_spec` composed from the backend's own `CliSpec` (`gogdl launch <dir> <id> --platform windows` for GOG, `nile launch <id>` for Amazon), `LaunchMode::StoreClient` is that shape, and `prepared.prefix` stays `None` because the store client owns its own Wine/Bottles runtime — the profile's environment and the wrapper chain still apply, but no umu key is set, so a transparency panel never claims a prefix the client would ignore. `stores::launch::launches_by_id(store)` is the one predicate the GUI's `play_is_wired()` and `runtime::client_launch` ask. `runtime::compose_handoff(game, runtime, report)` is the one composition shared by `app::play`'s worker and the detail page's Command panel, so the line a non-Steam panel previews and the process Play starts cannot drift; the runtime editor for non-Steam rows is `docs/m2-runtime-editor.md`. **The umu values replace the profile's rather than duplicating them** (`push_env` overwrites in place), so a stale `GAMEID` cannot point two games at one prefix and the rendered command stays clean; wrapper chains flatten in front of `umu-run` via `core::launch`, and `PITAGAMES_SESSION=1` drops gamescope steps only. `start(&spec, &RunOptions)` spawns the child as a session leader (`setsid`), tees stdout+stderr to `<logs>/<store>-<id>-<nanos>.log`, and `Session::wait` returns `Outcome { code, signal, duration, log }` (`summary()` = `exited 0 after 1h 02m` / `stopped by signal 15 after 2s`); `cancel`/`terminate(pid, grace)` signal the whole group `SIGTERM` then `SIGKILL` after `DEFAULT_GRACE` (10 s) from a detached thread. The GUI half is `app::play` (framework-free `Play`/`Running`/`Last` with `begin`/`apply`/`label`/`stop`/`clear_last`, a `PlayChannel` shaped like `InstallChannel`, one `pitagames-play-<store>` thread per game that owns the `Session`); `main.rs` drains it into the header strip (`Playing <title>` + transcript + Stop, then the last verdict + Dismiss) and, on `Finished`, adds `Outcome::duration` to the row's playtime (`persist::record_playtime`) — a store game's only playtime counter. `GameEntry::play_is_wired()` is now `is_steam() || exe.is_some() || (installed && stores::launch::launches_by_id(store))`, so an Epic or imported row gets a working Play, a GOG/Amazon row gets one too through its own client, and `play_blocked()` supplies the detail page's sentence for the two rows that still cannot launch. - **The focus graph is `crates/input/src/focus.rs`** (`pitagames-input`, `docs/m2.5-focus.md`): the framework-free spatial layout the desktop and console shells share. `FocusId(u64)` is a screen-chosen stable id, `FocusNode { id, row, col }` one cell, and `FocusGraph` the cells plus the focused one, always sorted by `(row, col, id)` so iteration and tie-breaks never depend on registration order. `grid(item_count, columns)` builds the row-major grid whose ids are the indices (a zero column count behaves as one column), `focus`/`focus_index`/`focused`/`focused_node`/`focused_index` read and set focus, `resolve(action)` answers the next cell without moving, and `move_focus(action)` applies it (the first navigation enters at the first cell; non-navigation actions leave focus alone; an empty graph returns `None`). The resolver ranks every cell strictly in the direction by one key `(diagonal, primary*2+perpendicular, perpendicular, primary, row, col, id)` — a straight candidate always beats a diagonal one, the primary distance then the perpendicular distance break ties, and `(row, col, id)` makes the answer deterministic; when nothing is in the direction, `wrap` flips only the moved axis to its far end (right from a row's right edge lands on that row's leftmost cell, down from the bottom lands on the top of the same column), so a one-cell row/column is a dead end but never a trap. ## Non-negotiable design constraints

- **Renderer boundary:** only `crates/app` may use Dioxus/RSX. `core`, `db`, `stores`, `art`, `platform`, `mods`, `metadata`, `input`, `shim`, `cli` stay framework-free. No JS navigation, no DOM focus, no `localStorage`.
- **Art is served, not inlined:** the webview only gets `http://127.0.0.1:<random>/<token>/<sha256(url)>-<size>.webp` from the session loopback server; never `file://`, never base64-inline a grid. `<img>` is only rendered once the file exists on disk (placeholder otherwise).
- **Controller input** goes through `gilrs` in Rust. WebKitGTK does expose `navigator.getGamepads()` (via `libmanette`) — do not use it: it only works while focused and can't be tested headlessly.
- **No `<video>`** in the v1 UI. It would bind the UI to GStreamer/WebKit and block the planned Blitz (`dioxus-native`) migration.
- **Launch composition is argv-only.** `LaunchSpec` is the single artifact shared by GUI, CLI and shim; never build shell strings or use `sh -c`. The shim's per-game config is the `ShimProfile` JSON (`core::profile_file`, written atomically); the shim applies its env and wrapper chain as vectors too.
- **Steam config writes** require Steam closed, atomic replace, a timestamped backup, and byte-identical restore. Round-trip tests for `localconfig.vdf` are mandatory. Reading it (playtime/last played) already lives in `stores::steam` and is side-effect free. The writer is `stores::vdf_edit` (shared span splicing) + `stores::localconfig`/`stores::compat_tool` (format-preserving edits) + `stores::steam_config` (closed-guard, one restore point per app/config file, journal + backup, atomic replace, exact-or-merged restore shared by both writers); `pitagames-cli launch-options` and `pitagames-cli compat-tool` are the diagnostics. Details in `docs/m1-launch-options.md` and `docs/m1-compat-tool.md`.
- **Secrets never leak by accident:** the only secret is the Steam Web API key, held as `pitagames_secrets::SteamApiKey` (no `Display`, redacting `Debug`, raw value behind `expose_secret`). It goes environment → desktop keyring → `0600` fallback file, and every API error is scrubbed of it. Never log, print or JSON-serialize a key; the UI shows `masked()` only.
- **One injection slot:** Tier A (Proton env), Tier B (manual OptiScaler), HelixSR and DLSSNR are mutually exclusive. Force `PROTON_USE_OPTISCALER=0` when DLSSNR owns `dxgi.dll`, and scan for conflicting files before install.
- **One mod manifest for every mod:** Tier B OptiScaler, HelixSR and DLSSNR all write `crates/mods`' `ModManifest` (`mods::manifest`): every file created, every original moved to `<game>/.gl-backup/`, a BLAKE3 hash per file, and a pre-install tree hash. Install validates paths before touching the tree; uninstall (`restore`) verifies the backups first and refuses a tampered one rather than clobbering, then reports whether the tree hash returned to the pre-install value. The `pitagames-cli mods` diagnostic shows, hashes, verifies and restores it. `blake3` is the mod/tree hash; `sha2` stays for release and Steam-config digests.
- **The mod primitives are shared, not per-system:** `crates/mods` also owns `mods::release` (a `Fetcher` trait with `ReleaseSource::{GitLab, GitHub}`; resolve a pinned release, download the named asset, verify its SHA-256 against a pin *we* ship — never only the API's digest — and unpack zip/zstd-tar/tar with zip-slip and symlink refusal), `mods::ini` (a line-preserving patcher driven by a per-mod data `IniSurface` — comments, ordering and CRLF survive, only an allowed key's value token changes, and an unknown section/key/value is refused), and `mods::capture` (every printed `%command%` line → an env map, keeping only the fixed allowlist `WINEDLLOVERRIDES`/`VK_ADD_LAYER_PATH`/`VK_INSTANCE_LAYERS`/`DXVK_*`/`VKD3D_*` and naming each reject). `pitagames-cli mods release|ini|capture` are the diagnostics, and `capture --run` drives the shared `stores::cli` PTY driver. Details in `docs/mods-primitives.md`.
- **Never redistribute** DLSSNR model weights (`nvngx_dlssnr.dll` is NVIDIA's) or HelixSR built artifacts. Run upstream installers unmodified in a PTY and capture the launch-option lines they print.
- **DLSSNR scope:** `optiscaler` route only, x86_64 only. Backend comes from GPU architecture (RDNA 4 → upstream GitLab project; RDNA 3 → `mauri870/DLSSNR-RDNA3` fork, `experimental`); never offer one architecture's package to the other.
- **Console session:** `PITAGAMES_SESSION=1` must suppress the per-game gamescope wrapper. Nested gamescope is a bug.
- **Safe mode:** `--safe-mode` disables the DMABUF renderer, animations and blur; webview init failure must auto-retry into it. A black screen with no keyboard is unacceptable.

## Compatibility claims

- Only the RX 9070 and RX 5700 XT paths may ship as validated. Everything else (RDNA 3/2, NVIDIA, Intel) ships `experimental`/`unverified`, and the UI must say "not tested by us". No parity claims in docs or store copy.
- No TV is attached to either machine. 10-foot readability, overscan, focus return and the gamescope session ship marked "not tested on a TV" until community-validated.
