## Environment

- This machine is macOS (`darwin`); the target is Linux (Arch/CachyOS). The GUI cannot be built or run locally. Verification runs in an `archlinux:latest` container or on the two target machines. Don't add macOS code paths to make local runs work.

## Build & verify

- **Local (macOS host)** — build/test only the pure-Rust crates:
  `cargo test -p pitagames-core -p pitagames-db -p pitagames-art -p pitagames-metadata -p pitagames-platform -p pitagames-stores -p pitagames-secrets -p pitagames-shim -p pitagames-cli`
  plus `cargo clippy --all-targets` and `cargo fmt --all` over the same list. Do not build `crates/app` locally.
- **MSRV is 1.89** (edition 2024 + let-chains; `keyring` 4 needs 1.88, the single-instance `std::fs::File::try_lock` needs 1.89). Clippy's `collapsible_if` only suggests let-chains at that MSRV, which is why the pure crates use them; keep `rust-version` in `Cargo.toml` at 1.89 or higher.
- **The single-instance lock is `flock`-based** (`core::lock::InstanceLock`, `$XDG_DATA_HOME/pitagames/pitagames.lock`): the GUI takes it before creating its window; when it is busy, the second launch asks the running instance to come to the front through the activation socket and exits `0`. The shim and the CLI deliberately do not take the lock, so they still run alongside the GUI. It is advisory and released by the kernel on exit/crash. Details in `docs/m1-single-instance.md` and `docs/m1-desktop-integration.md`.
- **Desktop integration is generated, not installed:** `core::desktop` renders `packaging/pitagames.desktop` byte-for-byte (a `pitagames-core` test asserts it). On startup the GUI writes `$XDG_DATA_HOME/applications/pitagames.desktop` pointing at the running binary, unless a packaged entry exists in `XDG_DATA_DIRS` or `PITAGAMES_NO_DESKTOP_ENTRY` is set; `pitagames-cli desktop-entry [--print|--write|--remove] [--exec <path>] [--path <file>] [--json]` is the diagnostic (`--print > packaging/pitagames.desktop` regenerates the checked-in copy). Single-instance focus is a Unix socket (`core::activation`, `<data>/pitagames/instance.sock`, one line `focus` → `ok`, `0600`, stale files probed and removed): the GUI binds it after the lock and raises the window from the event loop, `pitagames-cli activate [--socket <path>] [--json]` is the client. The tray icon (`crates/app/src/tray.rs`) is built manually because Dioxus's `init_tray_icon` panics; without a StatusNotifier host the launcher runs without one, and because `libappindicator` panics inside `dlopen` when its library is missing, the build runs under `catch_unwind` with the panic hook muted. The window/tray icon is painted in `crates/app/src/icon.rs` (twinned with `packaging/pitagames.svg`). Close still quits: no close-to-tray. Details in `docs/m1-desktop-integration.md`.
- **Packaging lives in `packaging/`:** `PKGBUILD` (named `pitagames-git` until there is a release tag; `provides`/`conflicts=('pitagames')` already match the release name) installs `/usr/bin/pitagames`, `/usr/bin/pitagames-cli`, the shim as `/usr/lib/pitagames/pitagames-shim` with a `/usr/bin/pitagames-shim` symlink (Steam launch options contain that name), `pitagames.desktop`, the hicolor SVG `Icon=pitagames` resolves to, the AppStream metainfo (`io.github.pitapony.PitaGames`, launchable `pitagames.desktop`) and `compat/*.toml` to `/usr/share/pitagames/compat`. `depends` is what the binary actually links — `webkit2gtk-4.1`, `gtk3`, `openssl`, `xdotool` (for `libxdo`) — plus `libayatana-appindicator` (dlopen'd by the tray, invisible to `ldd`/`namcap`) and `xdg-utils`; `umu-launcher`, Proton builds, gamescope/MangoHud/gamemode and the store CLIs stay optdepends. `makepkg` refuses to run as root, so verify as a non-root user (`fakeroot`, `debugedit`, `git`; `makepkg -e` reuses the source/target tree), then `pacman -U`, `appstreamcli validate --no-net`, `desktop-file-validate` and `namcap`. No `.SRCINFO` is checked in for a `-git` package (it changes every commit); it is generated at AUR submission. Details in `docs/m1-packaging.md`.
- **The M2 store CLIs share one driver** (`stores::cli`, `docs/m2-cli-backend.md`): a `CliSpec` holds the program plus one argv template per command (`{id}`/`{dir}`/`{parent}`/`{name}` substituted verbatim, one pass, never a shell string), `CliHandle::spawn` runs it on a PTY (child is a session leader with the PTY as its controlling terminal), a reader thread tees raw bytes to `cli-<program>-<command>-<nanos>-<pid>.log` and streams parsed `ProgressEvent`s, and `next_event`/`write_stdin`/`cancel`/`wait` drive it. Timeouts are per run — idle 5 min + hard 6 h for installs, hard 10 min only for `CliOptions::interactive()` auth — and a timeout or `cancel()` sends `SIGHUP`, then `SIGKILL` to the process group after a 2 s grace. The tests use `#!/bin/sh` fake CLIs injected through `CliOptions::env["PATH"]` (POSIX built-ins only, verified in the Arch container, where `/bin/sh` is bash in POSIX mode); the two timeout tests synchronise through a marker file the fake CLI writes, not through sleeps, so they do not race startup. A PTY echoes typed input, so an auth run's log/tail can contain the pasted auth URL/code — local diagnostics only, never into SQLite or the UI. `CliCommand` covers list/auth/logout/sync/install/verify/launch/status/version; `install` templates interpolate `{id}`/`{dir}`/`{parent}`/`{name}`, and `verify`/`launch` may use `{dir}` too (an optional install dir — `gogdl` needs `--path` for both), while a `{dir}` a command cannot supply is a `CliError::Template`, never a dropped argument. A command whose `CliSpec` template is empty is `CliError::Unsupported` (never an argument-less run), and `StoreStatus` (`probe`d from `PATH`, `Ready`/`CliMissing`) lives here so every backend shares it. The driver starts the child in `$HOME` unless `CliOptions::cwd` is set, so a relative `--program` does not resolve; use absolute paths.
- **Run verdicts are shared too** (`stores::report`, `docs/m2-cli-backend.md`): some wrapped CLIs log an error and exit `0`, only the line layout differs, so `LogFormat::{Legendary,Nile,Gogdl}` (`[cli] INFO: …` vs `INFO [CLI]:\t …`; `Gogdl` is `gogdl`'s `[NAME] INFO:` and parses like `Legendary`), `LogLine { level, source, message }`, `RunReport` (`succeeded()` = exit 0 + no `ERROR`/`CRITICAL`/`FATAL` line, `exited_cleanly()` = exit 0 only, `log_lines()` for per-store markers), `RunFailure`/`require_success()` and the PTY-tolerant `extract_json` live there. `stores::epic` re-exports its types, so the split did not move any caller.
- **The first backend on that driver is Epic** (`stores::epic`, `docs/m2-epic.md`; `pitagames-cli epic …`): the `legendary` argv presets (`list --json`, `list-installed --json`, `status --offline --json`, `--version`, `auth --disable-webview`, `auth --delete`, `install {id} --base-path {parent} --game-folder {name} --yes --disable-sdl`, `verify {id}`, `launch --skip-version-check {id}`), the JSON parsers that tolerate a PTY-merged `[cli] INFO:` stream, DLC filtering (`metadata.mainGameItem`/`is_dlc`), the code-paste auth relay, and `install_dir()` = `<XDG_DATA_HOME>/pitagames/games/epic/<sanitized name>` (`core::paths::games_dir()` + `core::paths::safe_component`). **Two legendary exit-0 traps**: `verify` exits `0` for corrupt/missing files, so the verdict is parsed from the summary line (`VerifyReport`), and some refusals log an error and still exit `0`, so `RunReport::succeeded()` also requires no error line while `launch` uses `exited_cleanly()` because the game shares the PTY. The auth flow gets its verdict from `Epic::report(&CliCommand::Auth, outcome)`, because a refusal after the prompt also exits `0`. `PROGRESS_PATTERN` matches only legendary's download/verify lines, not the install summary's compression percentage. Fixtures in `fixtures/legendary/` are the shapes from legendary's source — **not yet driven against a real `legendary`**, which no target machine has.
- **The second backend is Amazon** (`stores::amazon`, `docs/m2-amazon.md`; `pitagames-cli amazon status|list|installed|sync|auth|logout|install|verify|launch`): the `nile` presets (`library list --json`, `library list --installed`, `library sync`, `auth --status`/`--login`/`--logout`, `install {id} --path {dir}`, `verify {id}`, `launch {id}`), `install_dir()` = `games/amazon/<safe title>` (the title comes from the cached library, else the id) and `amazon::config_dir()` = `$NILE_CONFIG_PATH/nile` or `$XDG_CONFIG_HOME/nile` (nile appends `nile` to the base). **The login is a browser sign-in plus a pasted redirect URL, not a TOTP prompt** — Amazon's 2FA happens in the browser and the pasted URL carries `openid.oa2.authorization_code`, so the CLI answers nile's ENTER prompt and relays one stdin line. **nile exits `0` for almost every failure**, so: library/install/verify/sync/auth use `succeeded()`, `verify` is a repair whose verdict is the error lines (`amazon::VerifyReport`), and `launch` needs `amazon::launched()` (exit 0 **and** nile's `INFO [LAUNCHER]: Launching` marker) because a refusal also exits `0`. `library list --json` has no installed flag, so the installed set comes from the text listing (`Title ID: …`, split on the *last* ` ID: `) and nile's own `installed.json` only supplies path/version/size (a broken cache costs the paths, not the rows); `product.title` can be `null` → the id is the fallback. `PROGRESS_PATTERN` matches the bare `= Progress: 12.34 …` line (no `%` sign) and not the neighbouring `= Downloaded:` line. Every Amazon `Game` is tagged `platform:windows`; upstream's FuelPump "might not work" note is UI copy, not a backend guess. Fixtures in `fixtures/nile/` are the shapes from nile's source — **not yet driven against a real `nile`**.
- **The third backend is GOG, and it drives two CLIs** (`stores::gog`, `docs/m2-gog.md`; `pitagames-cli gog status|list|auth|install|verify|launch`): `lgogdownloader` owns the library and login (`--list json` is the only listing with titles, `--browser-login` is a browser-URL-plus-pasted-redirect flow, `--check-login-status` answers "signed in?" offline and exits `1` when signed out), while `gogdl` owns games (`--auth-config-path <file> download {id} --path {dir} --platform windows`, `repair`, `launch {dir} {id} --platform windows`). The two are **not interchangeable** — lgogdownloader only fetches installer files and has no launch command, and gogdl cannot list the library — so `Gog::spec_for(command)` routes each command to the program that supports it and the plan's "prefer lgogdownloader for install/verify" was corrected. `--auth-config-path` must precede the subcommand (argparse main-parser option); the auth file is `$XDG_CONFIG_HOME/pitagames/gog/auth.json`, never Heroic's. `--list json` is a `gameDetails` array (`product_id`/`gamename`/`title`, DLCs nested under `dlcs[]`, so no DLC filter is needed); the id is the numeric `product_id`. **`gogdl` exits non-zero on failure** (unlike legendary/nile), so library/install/verify use `succeeded()` and `launch` uses `exited_cleanly()`; its `[NAME] INFO:` lines share legendary's bracketed layout (`LogFormat::Gogdl`). `CliCommand::Verify`/`Launch` gained an optional install dir so `gogdl`'s `--path` can be filled (a missing dir is a `Template` error). No installed listing (`gogdl` has none; lgogdownloader's `--status` checks its own directory), so `verify`/`launch` need `--dir`; Windows platform only; no logout/sync. Fixtures in `fixtures/lgogdownloader/` are the shapes from its source — **not yet driven against a real `lgogdownloader`/`gogdl`**.
- **Live store metadata** is only reachable from the Linux container on this host (raw TCP to Steam times out locally while `curl` works). `pitagames-cli metadata <appid>` is the diagnostic; fixtures cover the parser locally. Details in `docs/m1-metadata.md`.
- **The Steam Web API key** is the only secret, in `crates/secrets`: `PITAGAMES_STEAM_API_KEY` → desktop keyring → `$XDG_CONFIG_HOME/pitagames/secrets/steam-api-key` (`0600`). A container has no session keyring, so `pitagames-cli steam-account --set-key` lands in the fallback file with a warning; that is expected. `pitagames-cli steam-account [--refresh]` is the diagnostic. Details in `docs/m1-owned-games.md`.
- **Proton discovery depends on the host**, so `platform::proton` tests pass explicit roots and the CLI can too: `pitagames-cli proton` prints every root it scanned plus the auto choice, and accepts `--root`/`--steam-root`/`--json` for fixture trees. Details in `docs/m1-proton.md`.
- **Steam config writes are fixture-verified**, not live-Steam-verified yet. The writer refuses when `/proc` shows Steam running; macOS reports `Unknown`, so local smoke runs need `--force` and an explicit `--localconfig`/`--backup-dir`. Use `pitagames-cli launch-options <appid> --shim --dry-run` first. Details in `docs/m1-launch-options.md`.
- **The shim profile is fixture-verified too**: the GUI writes `profiles/steam-<appid>.json` and the shim reads it. `pitagames-cli profile <appid> [--dir <path>] [--json]` prints it, and `pitagames-shim --explain <appid> [command]` prints the resolved env + command; point `XDG_DATA_HOME` at a fixture tree to run either without a GUI. `platform::envc` compiles the M1 runtime subset only — injected upscalers / frame-gen / neural rendering are refused by name until M3. Details in `docs/m1-profile.md`.
- **GUI verification** runs in an `archlinux:latest` container: build `crates/app` there after installing `rust webkit2gtk-4.1 gtk3 libsecret sqlite pkgconf openssl xdotool` (clippy/rustfmt ship inside Arch's `rust` package; `libudev` arrives via `systemd-libs`; `xdotool` supplies `libxdo` which dioxus-desktop's tray/menu deps link against). For an Xvfb smoke run add `xorg-server-xvfb dbus mesa imagemagick`: start `Xvfb :99`, run the GUI under `dbus-run-session`, drive it with `xdotool`, screenshot with `import -window root`. The Dioxus surface is compile-checked there first; never add macOS fallbacks to make the local toolchain happy. The container installs no status-notifier library, so only the tray's failure path is covered there.
- **The library grid is windowed** (`crates/app/src/grid.rs`, framework-free and unit-testable): the `LibraryGrid` component mounts only the visible rows plus `OVERSCAN_ROWS`, keeps a full-height sizer so the scrollbar stays accurate, and owns its scroll/measure signals so a scroll tick re-renders only the grid. Details in `docs/m1-virtualized-grid.md`.
- **The compat DB is files, not SQLite**: shipped `compat/*.toml` (baseline) + `$XDG_CONFIG_HOME/pitagames/compat/*.toml` (field-by-field overrides), loaded by `platform::compat`. `PITAGAMES_COMPAT_DIR` replaces the shipped dirs so a checkout works without an install; `pitagames-cli compat [--shipped <dir>] [--user <dir>]` is the diagnostic, and a test asserts the repository's own `compat/` loads warning-free. Unknown keys/values are rejected at load. Nothing selects an architecture yet — `platform::gpu` and the graphics screen are M3. Details in `docs/m1-compat-db.md`.
- **Anti-cheat detection is read-only and heuristic**: `platform::anticheat` walks a bounds-limited game directory (depth ≤ 3, ≤ 50k entries) for EAC/BattlEye markers and merges them with the compat DB's curated value — a real marker wins, otherwise curation is trusted (anti-cheat can live outside the game folder). `pitagames-cli anticheat <appid> [--dir <path>]` is the diagnostic; the detail page shows the card and the warning. `Unknown` never hard-gates, and the gate is **not enforced yet** (the graphics screen is M3). Details in `docs/m1-anticheat.md`.
- **Diagnostics toggles and logs are read-only**: the detail page's Runtime panel has Diagnostics chips (`runtime::DiagnosticsDraft` over `core::profile::Diagnostics`) and a resolved-command panel with a Copy button; the command is `core::launch::render_shell_command` (`runtime::resolved_command`), the same renderer as `pitagames-shim --explain`. `diagnostics.dxvk_log` → `DXVK_LOG_LEVEL=debug` (+ `DXVK_LOG_PATH`). The Logs tab and `pitagames-cli logs [--dir <path>] [--file <name>] [--tail n] [--grep text] [--json]` read `<XDG_DATA_HOME>/pitagames/logs` through `platform::logs` (bounded to 256 KiB from the end; never loads a whole file). Details in `docs/m1-diagnostics.md`.
- cargo on this machine needs `CARGO_HTTP_MULTIPLEXING=false` (libcurl stalls against the crates.io index; the sparse index then caches normally).

## Non-negotiable design constraints

- **Renderer boundary:** only `crates/app` may use Dioxus/RSX. `core`, `db`, `stores`, `art`, `platform`, `mods`, `metadata`, `input`, `shim`, `cli` stay framework-free. No JS navigation, no DOM focus, no `localStorage`.
- **Art is served, not inlined:** the webview only gets `http://127.0.0.1:<random>/<token>/<sha256(url)>-<size>.webp` from the session loopback server; never `file://`, never base64-inline a grid. `<img>` is only rendered once the file exists on disk (placeholder otherwise).
- **Controller input** goes through `gilrs` in Rust. WebKitGTK does expose `navigator.getGamepads()` (via `libmanette`) — do not use it: it only works while focused and can't be tested headlessly.
- **No `<video>`** in the v1 UI. It would bind the UI to GStreamer/WebKit and block the planned Blitz (`dioxus-native`) migration.
- **Launch composition is argv-only.** `LaunchSpec` is the single artifact shared by GUI, CLI and shim; never build shell strings or use `sh -c`. The shim's per-game config is the `ShimProfile` JSON (`core::profile_file`, written atomically); the shim applies its env and wrapper chain as vectors too.
- **Steam config writes** require Steam closed, atomic replace, a timestamped backup, and byte-identical restore. Round-trip tests for `localconfig.vdf` are mandatory. Reading it (playtime/last played) already lives in `stores::steam` and is side-effect free. The writer is `stores::vdf_edit` (shared span splicing) + `stores::localconfig`/`stores::compat_tool` (format-preserving edits) + `stores::steam_config` (closed-guard, one restore point per app/config file, journal + backup, atomic replace, exact-or-merged restore shared by both writers); `pitagames-cli launch-options` and `pitagames-cli compat-tool` are the diagnostics. Details in `docs/m1-launch-options.md` and `docs/m1-compat-tool.md`.
- **Secrets never leak by accident:** the only secret is the Steam Web API key, held as `pitagames_secrets::SteamApiKey` (no `Display`, redacting `Debug`, raw value behind `expose_secret`). It goes environment → desktop keyring → `0600` fallback file, and every API error is scrubbed of it. Never log, print or JSON-serialize a key; the UI shows `masked()` only.
- **One injection slot:** Tier A (Proton env), Tier B (manual OptiScaler), HelixSR and DLSSNR are mutually exclusive. Force `PROTON_USE_OPTISCALER=0` when DLSSNR owns `dxgi.dll`, and scan for conflicting files before install.
- **Never redistribute** DLSSNR model weights (`nvngx_dlssnr.dll` is NVIDIA's) or HelixSR built artifacts. Run upstream installers unmodified in a PTY and capture the launch-option lines they print.
- **DLSSNR scope:** `optiscaler` route only, x86_64 only. Backend comes from GPU architecture (RDNA 4 → upstream GitLab project; RDNA 3 → `mauri870/DLSSNR-RDNA3` fork, `experimental`); never offer one architecture's package to the other.
- **Console session:** `PITAGAMES_SESSION=1` must suppress the per-game gamescope wrapper. Nested gamescope is a bug.
- **Safe mode:** `--safe-mode` disables the DMABUF renderer, animations and blur; webview init failure must auto-retry into it. A black screen with no keyboard is unacceptable.

## Compatibility claims

- Only the RX 9070 and RX 5700 XT paths may ship as validated. Everything else (RDNA 3/2, NVIDIA, Intel) ships `experimental`/`unverified`, and the UI must say "not tested by us". No parity claims in docs or store copy.
- No TV is attached to either machine. 10-foot readability, overscan, focus return and the gamescope session ship marked "not tested on a TV" until community-validated.
